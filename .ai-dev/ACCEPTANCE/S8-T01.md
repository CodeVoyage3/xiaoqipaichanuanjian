## SQL / query plan 结论

- 搜索实际计划为 `SCAN tasks USING INDEX IX_tasks_product_id_open` + product 主键查找；当前 `instr` 搜索不能形成可选择性索引查找。
- Stage 查询同样扫描 open-task 索引，后续明细按 `IX_task_items_task_id_product_id` / batch 主键查找，但会形成约 25,000 个 task-id 参数。
- 历史列表扫描 `IX_inspections_task_id_product_id`，含 correlated item-count 子查询，并出现 `USE TEMP B-TREE FOR ORDER BY`；历史详情 item 排序也出现临时 B-tree。
- ProductTask 无变化聚合使用 `IX_tasks_product_id_status` 与 `IX_task_items_task_id_product_id`，当前代表路径很快。
- 诊断汇总：full scan=`true`、temp B-tree=`true`、过度 materialization=`observed`、UI 侧 `PageSize=int.MaxValue` 后内存筛选=`observed`、N+1=`not_proven`；timeout/lock/crash/OOM 均未出现。
- 对 100k 下在 DbCommand 拦截器之前失败的路径，已记录真实异常和耗时，但无法声称捕获到实际 SQL/EXPLAIN；这是证据限制，不是伪造空 SQL。
