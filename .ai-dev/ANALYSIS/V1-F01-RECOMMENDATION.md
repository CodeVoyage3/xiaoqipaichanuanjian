# V1-F01 推荐与影响分析（待产品经理确认）

## 推荐

推荐把“按商品大类的管理范围 + `policy_code/version`”作为独立首基线边界，并将历史过期补查候选设为：`ceil(批次实际保质天数 × 5%)`，端点包含，先不加本轮验证过的 7–60 截断（真实数据结果与未截断 5% 相同）。

理由：5% 在真实数据中产生 629 个补查、1,603 个仅历史基线，介于 3% 的 408/1,824 与 10% 的 1,176/1,056 之间；食品为主要历史积压来源（269/1,256），而家居、宠物、美妆仍得到非零且可控的补查。5% 不是已批准业务规则，只是用于产品决策的中位工作量候选。

不推荐把现行 30/14/7 或 90/60/14 Stage 窗口直接复用为历史补查窗口：该算法能被代码证实，但语义是未来阶段推进，不是历史追溯。也不推荐全应用单一首次导入开关：它会阻止新加入的品类独立建立可审计基线。

## 边界案例表

|案例|候选处理|不得发生的事|
|---|---|---|
|同 BatchKey 冲突（本表 25 组）|整体排除并报告|任挑一行导入或模拟|
|库存=0（本表无样本）|最高优先停止/只见过|创建可执行 Task 或当作新增到货|
|已过期且窗口内|历史补查候选|伪造已完成 Inspection|
|已过期且窗口外|仅历史基线|重置 seen 或 attention 水位|
|首次基线后新 BatchKey|正常新 Batch 生命周期|被全局初始化开关忽略|
|同 BatchKey 累计到货上升|仅首次超过历史最大值触发 attention|每次导入重复触发|
|正式提交后进入更高 Stage|按现有聚合规则再处理|以提交/基线永久封锁|
|生产日期缺失或日期倒置|不可分类，保留质量事实|用单位或有效日期反推生产日期|

## 预期实施影响（本任务不实施）

|区域|候选影响|
|---|---|
|Schema / migration|可能新增“范围基线”和“范围已见 BatchKey”持久化；需 migration，但本卡未创建。Product 的 category/policy 语义也需明确映射。|
|Import|Reader 可继续复用；Classifier 需从食品硬过滤变为范围映射 + policy 验证，仍保留冲突组与局部增量。Planner/Executor 不再硬编码 food。|
|Lifecycle / Task|保持 `ExpiryStageCalculator`、0 库存、max arrival、attention 和 `ProductTaskAggregator` 权威；在其前添加首基线分类门。历史补查的 task 创建需独立来源和批准。|
|Reminder|不另建提醒规则；仅现有 open task 通过 `InspectionTaskQuery` 进入提醒。|
|UI|导入、空状态和筛选文案从“食品”改为管理范围；应展示范围/策略/基线状态及不可分类问题，但不在 UI 重算规则。|
|Tests|新增范围级幂等、新品类、历史分类、冲突、0库存、new Batch、arrival max、Stage 升级与“不伪造历史”测试；不得删除既有食品回归。|

产品经理需先确认范围映射、5% 规则和历史补查的任务语义，之后才可拆实施任务；本建议不授权生产代码、migration 或 Stage 8。
