## 一、目标与交付边界

把 Stage 2 已验收的 Excel 导入主链接入真实 WPF：

`选择 .xlsx → 解析/分类/规划 → 展示预览与异常 → 确认 → 原子导入及生命周期编排 → 刷新首页与待排查任务列表`

本卡是 UI 接线，不重写导入引擎。UI 只负责选择、展示、确认、反馈和刷新；导入合法性、Product/Batch 更新、Import/ImportIssue、原始工作簿保存、快照、撤销边界和任务生命周期继续由既有 Application/Infrastructure 能力负责。

## 二、权威既有主链

实现必须按以下顺序复用具体类型，不得建立平行解析器、校验器、状态机或持久化路径：

1. `ExcelTemplateReader.Read(absolutePath)`：只读解析固定 `.xlsx` 模板并冻结文件名、SHA-256 与行 DTO。
2. `ExcelFileClassifier.Classify(workbook)`：复用食品行筛选、行问题、重复行、批次冲突和库存冲突判定。
3. 在一次独立后台生命周期内创建并释放 `StoreDbContext`，调用 `ExcelImportPlanner.Plan(context, classification)`；规划必须保持只读。
4. `ImportConfirmationGuard.BindPreview(absolutePath, workbook, plan)` 绑定预览身份。
5. 用户点击确认时调用 `ImportConfirmationGuard.Confirm(identity)`；只在 `CanConfirm == true` 且 `Contract != null` 时继续。
6. 使用新的、无跟踪实体的 `StoreDbContext` 调用 `ConfirmedImportLifecycleOrchestrator.Execute(context, request)`。不得绕过它直接调用 `ConfirmedImportExecutor`。
7. 仅以 `ConfirmedImportResult.Succeeded / Code / SafeUserMessage / ImportId` 作为确认结果；不得从异常文本反推业务状态。

`ConfirmedImportLifecycleRequest` 使用：

- `Contract`：确认守卫本次返回的冻结契约。
- `SnapshotDirectory`：应用自有 `%LocalAppData%\StoreExpiryInspector\backups\pre-import`；不得让用户绕过快照。
- `ParsedAtUtc`：本次成功完成预览时冻结的 UTC 时间。
- `BusinessDate`：确认动作发生时的本地业务日期。
- `OccurredAtUtc`：确认动作发生时的 UTC 时间。

不得把 Stage 3 生命周期规则塞进 `ConfirmedImportExecutor`、ViewModel、code-behind 或新的 UI 协调器。

## 五、文件选择与预览

- 使用 WPF/Windows 自带 `Microsoft.Win32.OpenFileDialog`，筛选 `.xlsx`；不增加依赖。
- 未选择文件时显示明确初始态和“选择 Excel”按钮，确认按钮不可用。
- 取消选择是正常无操作：不报错、不清空已有已完成预览、不触发解析。
- 选中新文件后立即进入解析 Loading；解析期间“选择 Excel”“确认导入”“Retry”不得发起并发操作。
- 文件路径仅用于调用既有能力；页面主要显示文件名，不默认暴露完整本地路径。
- 解析成功后至少显示：文件名、涉及商品数、正常批次键数、新增/更新商品数、新增/更新批次数、跳过行/行问题/重复行/批次冲突/库存冲突/规划问题数量、是否有变化。
- 可展示问题必须直接来自 `ImportPreview` 及其既有集合；行号、商品编码、字段、既有安全摘要按实际 DTO 能力展示。UI 不合并冲突为新的业务结论，也不决定某行能否导入。
- `Plan.HasChanges == false` 时展示既有“无需确认导入”语义，确认按钮不可用；这不是失败。
- 解析器抛出的文件格式、缺失、权限或 IO 异常显示稳定中文安全文案，详细异常写既有本地日志，禁止静默失败或直接暴露堆栈。

## 六、确认与结果

- 预览成功时保留同一次 `ImportPreviewIdentity` 与 `ParsedAtUtc`；确认不得根据页面字段重建 `ImportPlan`。
- 确认前必须再次经过 `ImportConfirmationGuard.Confirm(identity)`，以既有结果处理文件变化、丢失、不可读和无变化。
- 确认中显示明确 Loading，禁止再次选择、再次确认或并发 Retry；重复点击只能执行一次导入。
- 只调用 `ConfirmedImportLifecycleOrchestrator`，确保快照、Import/ImportIssue、原始工作簿、Product/Batch 更新和 Stage 3 生命周期仍在既有原子边界内完成。
- 成功显示明确成功反馈与 ImportId（有值时）；成功契约保持不可再次提交。用户可重新选择另一文件开始新预览。
- 失败显示 `ConfirmedImportResult.SafeUserMessage` 或稳定安全错误，并保留 Retry/重新选择能力；禁止吞成成功、空状态或无反馈。
- `stale_plan`、`file_changed`、`file_missing`、`file_unavailable` 必须要求重新解析，不得盲目重放旧契约。
- 其他可重试执行失败允许用户对当前冻结预览再次点击 Retry，但每次仍须重新经过确认守卫；不得创建 UI 自有导入状态或 Import 记录。

本卡不提供 Undo 按钮，也不调用 `ImportUndoEligibilityService`；只保证现有成功 Import 的撤销资格边界不被破坏。

## 七、展示状态与并发

ViewModel 只维护展示状态，至少真实覆盖：

- 初始/未选择文件。
- 文件选择取消。
- 解析中。
- 解析成功且可确认。
- 解析成功但无变化/不可确认。
- 有警告或异常明细。
- 解析失败。
- 确认中。
- 导入成功。
- 导入失败。
- Retry。

沿用 S4-T05 的最小 `INotifyPropertyChanged`、`RelayCommand` 和版本号防陈旧结果模式。解析与确认离开 UI 线程；每次操作使用自己的 `StoreDbContext`，不跨线程共享 Context、DbSet、IQueryable 或 tracked entity。

命令 CanExecute 和关键派生属性必须在状态变化时通知。无论成功或失败都必须结束 Loading。较早异步操作的迟到结果不得覆盖较新选择或结果。

## 八、成功后的页面联动

只有 `ConfirmedImportResult.Succeeded == true` 后才触发：

1. `await Dashboard.LoadAsync()`。
2. `await PendingTasks.LoadAsync()`。

刷新复用现有 ViewModel，不新建事件总线、缓存或刷新服务。待排查列表保留当前搜索、canonical 阶段筛选和可用页码语义；若导入后当前页越界，沿用 Application 返回与现有分页边界做最小归位，不在 UI 全量加载后二次分页。

刷新失败不得把已经成功提交的导入显示为失败：成功反馈保留，同时明确提示“数据已导入，但页面刷新失败”，记录详细异常并提供页面 Retry。不得要求用户重启应用才能看到新数据。

## 九、错误与日志

- UI 对未捕获的解析/协调异常显示稳定安全文案；既有 `SafeUserMessage` 原样作为业务安全反馈。
- 详细异常继续写 `%LocalAppData%\StoreExpiryInspector\logs` 的既有 `LocalFileLogger`。
- 禁止空 catch、静默失败、按钮无反馈、异常直接变空列表或把异常 `Message` 当状态码。
- 导入成功后的刷新错误与导入事务失败必须分别呈现。
