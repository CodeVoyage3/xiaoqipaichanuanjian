## 目标

消费 S2-T04 已冻结的确认契约、S2-T03 差异计划和 S2-T05 安全快照能力，在用户正式确认后执行一次原子的 SQLite 增量写入。任何数据库步骤失败都必须回滚全部正式业务写入；已经成功创建的导入前快照文件必须保留。

本卡不重新解析、分类或规划 Excel，不计算效期或执行生命周期状态转换。

## 固定流程

严格保持以下顺序：

1. 校验 S2-T04 `ImportConfirmationContract` 的结构、状态、冻结工作簿字节、SHA 和 `ImportPlan.HasChanges`。
2. 在创建快照前重新只读打开 `SourceFilePath`，重新计算 SHA-256；路径、文件名、内容哈希必须仍与契约一致。失败要求重新解析/预览，不写库、不创建快照。
3. 取得当前 `StoreDbContext` 对应的 SQLite 文件路径，调用现有 `PreImportSnapshotService` 创建并验证快照。失败立即阻断，不开启写事务。
4. 快照成功后开启一个明确的 EF/SQLite 数据库事务。
5. 在事务内核对计划与当前数据库仍一致，拒绝过期或被篡改的计划。
6. 创建正式 Import，状态只允许 `Succeeded`。
7. 按现有计划写入本次实际涉及的 Product / Batch 增量及 `last_seen_import_id`。
8. 写入 S2-T02/S2-T03 已交付的问题事实。
9. 保存确认契约中冻结的原始工作簿字节。
10. 保存快照关联元数据，完成最终 SaveChanges 后提交同一事务。

除快照文件外，任何第 4～10 步失败均必须回滚为事务开始前状态。

## 入口与结果契约

一个具体执行器至少接收：

- 已由 S2-T04 生成的 `ImportConfirmationContract`。
- 当前 `StoreDbContext`。
- 导入前快照目标目录。
- 解析时间 UTC；确认时间由执行当次 UTC 产生或由最小可测试时钟参数传入。

不得接收裸 `ImportPlan` + 裸 byte[] 绕过确认契约。

结果至少提供：

- `Succeeded` / 等价布尔值。
- 稳定结果代码和安全摘要。
- 成功时 Import ID、快照路径；失败时 Import ID 必须为空。
- 快照创建后的事务失败结果仍返回本次快照路径或元数据，证明安全副本未被删除。

至少区分：`invalid_contract`、`file_changed` / `file_unavailable`、`snapshot_failed`、`stale_plan`、`transaction_failed`、`succeeded`。不得向安全摘要泄露堆栈、连接字符串或工作簿内容。

## 确认契约与文件身份

- 契约必须为 `TargetImportStatus == Succeeded`、计划有真实 Product/Batch 变化、冻结字节非空、契约 SHA 为小写 64 位十六进制，且冻结字节重新计算 SHA 一致。
- 源路径必须为绝对文件路径，文件名必须等于契约文件名。
- 正式执行前重新读取当前源文件并计算 SHA；不允许只信任 S2-T04 较早时刻的结果。
- 文件缺失、锁定、替换、修改或哈希不一致时不得创建快照、不得开启事务、不得创建 Import。
- 工作簿最终保存契约内的冻结字节；不得在事务中第三次解析 Excel，也不得从变化后的路径读取另一份内容。

## 快照与数据库定位

- 必须从当前 SQLite context/connection 获得实际数据库文件路径，禁止调用默认 `%LOCALAPPDATA%` 数据库或依赖调用方另传一个可能不一致的源路径。
- 内存数据库、非 SQLite provider、空/不可解析数据源均拒绝执行。
- 使用现有 `PreImportSnapshotService`；只有 `CanProceed = true` 且元数据再次通过必要校验时才允许开启写事务。
- 成功 Import 的 `PreImportSnapshotPath` 必须等于该元数据的最终绝对路径。
- 在同一正式事务内新增一条 `BackupRecord`：`pre_import`、快照绝对路径、快照 SHA、快照创建 UTC、`verified`。该记录与 Import 一起成功或回滚；不得重复创建第二个快照。
- 事务失败时快照文件保留，不删除、不回滚文件；事务内 BackupRecord 随数据库事务回滚。结果仍须把快照路径返回给上层用于诊断/后续治理。

## 事务前计划一致性门禁

快照成功、事务开启后，在首次正式写入前重新按商品编码与批次唯一键查询本次计划涉及的数据并验证：

- NewProduct 的编码当前仍不存在；Updated/Unchanged Product 当前仍存在且计划中的已知旧值与数据库一致。
- NewBatch 的唯一键当前仍不存在；Updated/Unchanged Batch 当前仍存在且计划中的已知旧值与数据库一致。
- ProductUpdate / BatchUpdate 的 `FieldChanges` 字段只能来自当前 S2-T03 白名单，`Before` 必须与数据库当前值精确一致，`After` 类型和值必须符合目标字段。
- 新批次所引用商品必须来自同一计划的新商品或当前已核对的历史商品。
- 计划集合不得出现同商品编码、同批次唯一键重复或相互矛盾的 New/Updated/Unchanged 动作。

任一不一致返回 `stale_plan`，事务内不得留下任何写入，快照继续存在。不得为“尽量导入”而重新查询后悄悄重算 diff，也不得静默覆盖预览后的数据库变化。

## Import 正式事实

Import 必须写入：

- SourceFileName / SourceFileSha256：来自确认契约。
- ParsedAtUtc / ConfirmedAtUtc：UTC，且确认时间不早于解析时间。
- Status：精确为 `Succeeded`；`IsUndone = false`、`UndoneAtUtc = null`。
- ProductCount：Preview.InvolvedProductCount。
- BatchCount：Preview.NormalBatchKeyCount。
- NewProductCount / NewBatchCount / UpdatedBatchCount：来自计划实际集合数。
- IssueCount：精确等于本事务实际持久化的 ImportIssue 数。
- UnsupportedCategoryCount：Preview.SkippedRowCount；非食品跳过不作为 ImportIssue。
- NewTaskProductCount：固定使用契约占位 `0`，不得计算或解释任务数量。
- PreImportSnapshotPath：本次已验证快照绝对路径。

解析、预览、失败、取消、无变化或 stale plan 不创建正式 imports 记录。

## Product 增量应用

- NewProduct 只写计划中 ProductCode、CurrentName、CurrentBarcode、CategoryCode=`food`、PolicyCode=`food_v1`、ExcelStockQty、EffectiveStockQty、EffectiveStockSource=`excel`，使用现有默认生命周期基础字段，不额外产生状态动作。
- UpdatedProduct 只允许应用 `CurrentName`、`CurrentBarcode`、`ExcelStockQty`、`EffectiveStockQty`、`EffectiveStockSource` 五种 S2-T03 字段变化。
- 库存冲突时 S2-T03 不产生库存字段 change；执行器不得从 Preview/原始行另选某个值补写。
- 合法库存 `0` 只保存库存事实；不得改变商品或批次生命周期状态。
- 本次计划中 New/Updated/Unchanged 且实际正常出现的 Product 均更新 `LastSeenImportId`；只更新时间戳等必要审计字段。
- 不在计划内的历史 Product 完全不查询后批量更新，尤其不得更新 `LastSeenImportId`。

## Batch 增量应用

- 新批次严格按两种既定唯一键创建，写 ShelfLifeValue/Unit、CurrentArrivalQty、MaxArrivalQty、SourceDiscountReference 和 `LastSeenImportId`；默认 TrackingStatus/CurrentStage 只采用实体既有创建默认值。
- 已有批次只允许应用 `ShelfLifeValue`、`ShelfLifeUnit`、`CurrentArrivalQty`、`MaxArrivalQty`、`SourceDiscountReference` 五种计划变化。
- `MaxArrivalQty` 只在本次合法 CurrentArrivalQty 大于历史值时升高，永不降低；必须使用 S2-T03 已规划的 After，不在执行期据此触发任何业务动作。
- 本次计划中 New/Updated/Unchanged 的正常 Batch 均更新 `LastSeenImportId`；冲突组、异常行和未出现历史批次不得更新。
- 禁止修改 LifecycleGeneration、TrackingStatus、StopReason、StoppedAtUtc、CurrentStage、NextTriggerDate、AttentionVersion、HandledAttentionVersion。

## 异常持久化口径

只消费 Preview 已有问题，不重新判断业务规则：

- 每个 RowIssue 写一条 ImportIssue：原行号、Code、FieldName、Summary。
- 每个 BatchConflict 的每个冲突行写一条 `batch_conflict`，行号保留，字段名由 DifferingFields 稳定拼接，摘要不包含工作簿原始敏感值。
- 每个 StockConflict 涉及的每个去重行号写一条 `stock_conflict`，FieldName 固定为库存总数字段；不得保存或选择冲突库存作为正式 Product 库存。
- 每个 PlanningIssue 写一条 ImportIssue，使用其行号、Code、FieldName、SafeSummary。
- DuplicateRow 是无须重复新增的重复事实，不作为异常；SkippedRow 是暂不支持分类，只计 UnsupportedCategoryCount，不作为异常。
- 持久化顺序必须稳定；Import.IssueCount 必须等于数据库中该 Import 的 ImportIssue 实际数量。

异常行/冲突批次不得出现在 Product/Batch 正常写入集合；同一文件中其他独立正常项可按计划写入。

## 原始工作簿

- 每个成功 Import 精确新增一条 ImportWorkbook。
- OriginalFileName、SHA 来自确认契约；Content 是契约冻结字节的独立副本；SavedAtUtc 为 UTC。
- 保存后重新计算 BLOB SHA 必须等于 Import 与契约 SHA；内容逐字节相同且非空。
- 本卡不删除历史工作簿，也不实现最近两份裁剪；该策略属于 S2-T07。

## 单事务与错误处理

- 使用 `BeginTransaction` / async 等价物显式包住 Import、BackupRecord、Product、Batch、ImportIssue、ImportWorkbook 的全部数据库写入和最终提交。
- 为获得 Import ID 允许在同一事务内分阶段 `SaveChanges`，但任何异常必须 Rollback；返回前清理/隔离 context ChangeTracker，防止调用方稍后误提交残留实体。
- 不捕获后继续提交，不把失败 Import 改写为 Succeeded，不创建 `Failed` 状态记录。
- 唯一约束、外键、I/O、SaveChanges 或 Commit 失败均返回失败结果；快照文件保留。
- 成功后使用全新 context 验证正式事实，不依赖当前 ChangeTracker 作为证据。

### 文件、快照与计划门禁

### 事务故障注入

至少分别在以下节点制造确定性异常：

1. Import 已插入后。
2. Product 写入过程中。
3. Batch 写入过程中。
4. ImportIssue 写入过程中。
5. ImportWorkbook 写入过程中。
6. 最终 SaveChanges 完成后、Commit 前或事务提交拦截点。

优先在测试中使用 SQLite 临时 trigger/约束或 EF 已有 interceptor；不得为此给生产代码增加通用故障框架。每个故障均以全新 context 证明：

- Import / BackupRecord / ImportIssue / ImportWorkbook 数量恢复到事务前。
- Product / Batch 无新增、无半更新，所有旧行逐字段恢复。
- 不存在 Succeeded 残缺 Import 或孤立子记录。
- 本次已验证快照文件仍存在、哈希不变、可打开。
- 执行器返回失败且 Import ID 为空；ChangeTracker 不会在后续 SaveChanges 中重新提交失败实体。

### 重复调用与数据库约束

- 同一个已消费计划再次执行时必须因计划陈旧/唯一键变化整体拒绝或回滚，不产生第二条残缺导入。
