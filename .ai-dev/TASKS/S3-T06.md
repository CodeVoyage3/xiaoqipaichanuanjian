## 目标

实现唯一、可复用的 Application 生命周期用例：调用方已经持久化合法正式排查，且指定批次的正式 `InspectionItem.CheckedQty == 0` 时，停止该 Batch 后续效期跟踪并写入批准的 LifecycleEvent。

本卡只负责 `正式批次 0 件事实 → Batch 停止 + batch_checked_zero 事件`。不创建或编辑正式排查，不完成 ProductTask，不处理 Draft，不实现 0→正数编辑恢复，也不接入 Stage 4 提交流程。

## 已核验的实际实体、关系与 canonical 值

仓库没有 `InspectionRecord` / `InspectionBatchRecord`；实际正式实体为：

- `Inspection`：`Id`、`TaskId`、`ProductId`、正式快照、`CheckDate`、`SubmittedAtUtc`。
- `InspectionItem`：`Id`、`InspectionId`、`ProductId`、`BatchId`、批次快照、`CheckedQty`、`UpdatedAtUtc`。
- `InspectionItemRevision`：保存正式明细后续数量修订历史；本卡不创建或编辑 Revision。
- `Batch`：复用 `TrackingStatus`、`StopReason`、`StoppedAtUtc`、`CurrentStage`、`NextTriggerDate`、`AttentionVersion`、`HandledAttentionVersion`、到货量和 lifecycle generation。
- `LifecycleEvent`：复用 `ProductId`、`BatchId`、`EventType`、`Reason`、`OccurredAtUtc`、`SourceInspectionId`。

现有数据库关系已经保证：

- Inspection 通过 `(TaskId, ProductId)` 归属商品任务，并以 `(Id, ProductId)` 为 alternate key。
- InspectionItem 通过 `(InspectionId, ProductId)` 归属 Inspection，通过 `(BatchId, ProductId)` 归属 Batch。
- `(InspectionId, BatchId)` 唯一，同一正式排查中每个 Batch 最多一个明细。
- LifecycleEvent 的 `(SourceInspectionId, ProductId)` 与 `(BatchId, ProductId)` 分别受 FK 约束。

本卡固定复用以下既有稳定代码：

- Batch 停止状态：`stopped`。
- Batch 停止原因：`batch_checked_zero`。
- LifecycleEvent 类型：`batch_checked_zero`。
- LifecycleEvent Reason：`batch_checked_zero`。

不得增加 `IsZeroChecked`、`Disabled`、平行停止原因、事件类型或生命周期字段。

## 最小输入与正式事实校验

新增一个具体 Application 用例和最小请求/结果类型。请求至少包含：

- `ProductId`：正整数。
- `BatchId`：正整数。
- `InspectionId`：正整数。
- `InspectionItemId`：正整数。
- `CheckedQty`：调用方明确传入，必须精确为 `0`；非 0 立即拒绝。
- `OccurredAtUtc`：显式 UTC 业务发生时间，不读取系统当前时间；不得早于正式 Inspection 的 `SubmittedAtUtc`。

在任何写入前必须从当前 StoreDbContext 验证：

1. Product、Batch、Inspection、InspectionItem 均存在。
2. Batch.ProductId、Inspection.ProductId、InspectionItem.ProductId 均等于请求 ProductId。
3. InspectionItem.InspectionId 等于请求 InspectionId。
4. InspectionItem.BatchId 等于请求 BatchId。
5. 持久化 `InspectionItem.CheckedQty` 当前精确为 `0`；不得只相信请求参数。
6. 请求时间为 UTC 且不早于正式记录提交时间。

任何 ID、归属、数量或时间不一致均拒绝整次调用且无副作用。不得扫描 Inspection 历史来猜测哪个批次为 0，也不得接收仅 ProductId/BatchId/整数 0 就停止任意 Batch。

## Batch 停止转换

只允许从结构一致的活动状态执行首次停止：

- `TrackingStatus == active`。
- `StopReason == null`。
- `StoppedAtUtc == null`。

首次合法执行：

- `TrackingStatus = stopped`。
- `StopReason = batch_checked_zero`。
- `StoppedAtUtc = OccurredAtUtc`。
- `NextTriggerDate = null`，使 S3-T03 的 `(tracking_status, next_trigger_date)` 查询不再命中。
- `UpdatedAtUtc = OccurredAtUtc`。
- 保留 `CurrentStage`，不计算或伪造新阶段。

必须逐字段保留：Batch 身份和日期、ShelfLife、Current/MaxArrivalQty、SourceDiscountReference、LifecycleGeneration、AttentionVersion、HandledAttentionVersion、LastSeenImportId、CreatedAtUtc。

本卡不改变 AttentionVersion。现有治理仅把“真正新增到货”定义为新关注事实；停止跟踪不需要伪造恢复版本。S3-T05 后续恢复时自行执行既有 compare-and-set。

如果 Batch 为 active 但携带停止原因/时间，属于不一致状态，拒绝且不修复。如果已经 stopped 且不是本卡同一正式事实的幂等重放，不覆盖原因、时间或其他状态，明确拒绝无副作用。

## 持久化幂等与恢复后旧事实重放

使用现有正式 LifecycleEvent 作为同一 0 件事实已经执行的持久化锚点。精确身份为：

`EventType == batch_checked_zero`

且同时：

- `ProductId == request.ProductId`
- `BatchId == request.BatchId`
- `SourceInspectionId == request.InspectionId`

调用仍须先完成正式 InspectionItem 归属和当前 CheckedQty=0 校验。若上述事件已经存在，则视为相同正式 0 件事实已处理，立即幂等成功且不修改任何状态或时间，不写第二条事件。

这一事件锚点必须覆盖两种重放：

- Batch 仍处于本次 `batch_checked_zero` 停止终态时重复调用。
- Batch 后来已由 S3-T05 因真正新增到货合法恢复为 active，再重放旧 Inspection/Item 请求。

后一场景必须保持恢复后的 Batch、AttentionVersion、任务和恢复事件不变，绝不能重新停止。

若 Batch 已为 `batch_checked_zero` 停止但不存在匹配来源事件，现有持久化事实不能证明是同一请求；不得补写或覆盖，按冲突拒绝。其他 StopReason 同理拒绝。

本卡不定义同一 InspectionItem 经历史编辑发生 `0→正数→0` 的新事实身份；0→正数恢复及多轮修订时序属于 Stage 5，届时必须基于正式 Revision 另行批准，不能绕过本卡当前的旧事实重放保护。

## LifecycleEvent

只有本次真实把 active Batch 首次转换为 stopped 时新增一条：

- `EventType = batch_checked_zero`。
- `Reason = batch_checked_zero`。
- ProductId、BatchId 为请求目标。
- `SourceInspectionId = InspectionId`。
- `SourceImportId = null`、`SourceAdjustmentId = null`。
- `OccurredAtUtc` 原样使用已验证请求时间。

不得为拒绝、既有停止状态或幂等重放伪造事件。事件是审计与幂等事实，不代替 Batch 当前状态。

## 与 S3-T03、S3-T05 的衔接

- 停止后 `TrackingStatus=stopped` 且 `NextTriggerDate=null`，S3-T03 不得再命中。
- 写出的 `StopReason=batch_checked_zero` 是 S3-T05 唯一可恢复原因。
- 组合测试必须真实调用 S3-T05：旧最高未突破时不恢复；首次突破且 Product 从未归零、库存大于 0 时恢复并写 `batch_tracking_resumed`。
- S3-T04 商品归零仍为最高优先级；商品后来正式归零后，S3-T05 永久不恢复该旧 Batch。
- 不修改 S3-T03/S3-T04/S3-T05 生产逻辑，不复制其规则。

## 事务边界

目标 Batch 更新与 LifecycleEvent 新增必须使用同一个 StoreDbContext 和数据库事务：

- 当前无事务时，本用例拥有事务并统一提交/回滚。
- 当前存在外层事务时，本用例加入当前事务，不嵌套 commit/rollback；由 Stage 4 调用方最终统一提交或回滚。
- LifecycleEvent 写入或 SaveChanges 中途失败时，Batch 停止状态和事件整体回滚。
- 自有事务失败后清理 ChangeTracker，避免后续误提交；外层事务内异常时恢复本卡触碰实体的 tracked 状态但不抢先处理调用方事务。
- 不增加生产故障开关；使用真实 SQLite trigger/约束注入失败。
