## 目标

实现一个独立的 Application 用例：软件启动或恢复运行时，由调用方显式传入业务日期，对已经到达 `next_trigger_date` 的活动批次直接补算到当前阶段，并复用 S3-T02 将待排查批次聚合进商品唯一开放任务。

本卡只实现可被后续真实启动入口调用的 Application 能力；不接入 `App.xaml.cs`、WPF、托盘、提醒或电源恢复事件。

## 已核验的仓库事实与字段语义

- Batch 已有 `TrackingStatus` / `tracking_status`、`CurrentStage` / `current_stage`、`NextTriggerDate` / `next_trigger_date`、`AttentionVersion` / `attention_version`，无需新增平行字段。
- `BatchConfiguration` 已有 `IX_batches_tracking_status_next_trigger_date` 复合索引，查询必须以 `tracking_status = 'active'` 和 `next_trigger_date <= 业务日期` 为数据库过滤条件利用该索引。
- S3-T01 的 `ExpiryStageCalculator.Calculate(...)` 是阶段和下一触发日的唯一计算实现，canonical 阶段为 `none / discount_50 / discount_20 / withdraw / expired`。
- S3-T02 的 `ProductTaskAggregator` 是商品开放任务与 TaskItem 聚合的唯一实现；它支持加入调用方开启的外层事务，并校验当前事务可见的 `Batch.AttentionVersion`。
- `AttentionVersion` 表达批次关注事实版本，现有治理把真正累计到货变化作为其后续使用场景；效期阶段自然推进本身不创造新的关注版本。S3-T02 已能在已有 Draft 时因原 TaskItem 阶段升级而保留内容并标记重新确认。
- 因此本卡不得递增、重置或以阶段优先级改写 `AttentionVersion` / `HandledAttentionVersion`。向聚合器传入批次当前既有 `AttentionVersion`；阶段升级的 Draft 重新确认继续由 S3-T02 处理。
- 当前 schema、索引和事务能力足以承载本卡，默认不新增 migration。

## 输入与结果契约

调用方必须显式传入：

- `businessDate`：本次补算业务日期，类型为 `DateOnly`。
- 写入 `Batch.UpdatedAtUtc` 及调用 S3-T02 所需的 UTC 时间戳也必须由调用方显式提供；不得在用例内部读取系统时钟。该时间戳必须明确为 UTC。

返回一个普通结果值，最少表达：

- 命中并重新计算的批次数。
- 实际发生 Batch 状态变化的批次数。
- 交给 S3-T02 聚合的待排查批次数或商品数。

结果不得返回 tracked EF 实体、Task/Draft 可写对象、历史阶段列表或 UI 文案。

## 数据库查询门禁

候选批次必须由数据库查询直接限定为：

- `TrackingStatus == "active"`。
- `NextTriggerDate != null`。
- `NextTriggerDate <= businessDate`。

要求：

- 过滤条件必须保留为可翻译的 EF LINQ 表达式，在 materialize 前完成。
- 不得先读取所有 Batch、所有活动 Batch 或历史 Inspection 后在内存筛选。
- 不得扫描 Inspection、Task 或 LifecycleEvent 历史推导当前阶段。
- 真实 SQLite 测试必须检查生成 SQL 和/或 `EXPLAIN QUERY PLAN`，明确证明候选查询使用 `IX_batches_tracking_status_next_trigger_date`，而不是全表扫描。
- 只允许随后针对命中批次及其商品执行 S3-T02 必需的定向查询。

## 核心流程

1. 开启一个清晰的外层数据库事务。
2. 通过上述数据库条件一次取得当前到期的活动批次；无命中时直接返回无变化结果。
3. 对每个命中批次只调用一次 S3-T01：
   `ExpiryStageCalculator.Calculate(businessDate, ExpiryDate, ShelfLifeValue, ShelfLifeUnit)`。
4. 直接使用计算得到的唯一 `CurrentStage` 和 `NextTriggerDate`；不得逐日循环、阶段回放或生成历史阶段序列。
5. 仅当值实际变化时更新 Batch 的 `CurrentStage`、`NextTriggerDate` 和调用方提供的 `UpdatedAtUtc`；完全相同结果不得制造无意义写入。
6. `none` 只允许更新 Batch 计算结果，不创建待排查 TaskItem/Task。
7. 对 `discount_50 / discount_20 / withdraw / expired`，按 Product 分组，每个商品调用 S3-T02 `ProductTaskAggregator` 一次；每个输入保留自身当前阶段与既有 `AttentionVersion`，不得复制任务聚合逻辑。
8. 最终由外层事务统一提交；任一批次、任务、Item 或 Draft 处理失败时统一回滚。

同一批次离线跨越多个阶段时，只得到业务日期当天的计算结果。例如 `none` 关闭数日后已进入 `withdraw`，本次只更新为 `withdraw` 并生成/升级当前收仓任务，不生成 `discount_50` 或 `discount_20` 历史任务。

## AttentionVersion 与 S3-T02 调用契约

- 本卡的自然日期推进不改变 `Batch.AttentionVersion`，因此不需要为版本变化执行预聚合 SaveChanges。
- 必须将批次当前既有 `AttentionVersion` 原样传给 `ProductTaskAggregator`。
- 不得把阶段变化伪装为关注版本变化，也不得设置“累计到货变化”的显式重新确认原因。
- 对已有 TaskItem 的自然阶段升级，聚合器按 S3-T02 既有规则更新原 Item，并在存在有效 Draft 时保留草稿内容、设置 `RequiresReconfirmation`。
- 若实现过程中发现必须改变 AttentionVersion 才能满足现有约束，立即停止并报告 Sol；不得自行改写版本语义或新增字段。

## 事务边界与失败安全

Batch 更新以及 S3-T02 可能写入的 ProductTask、ProductTaskItem、Draft 重新确认状态必须位于同一个 `StoreDbContext` 和同一个外层事务。

- 用例拥有外层事务及最终提交/回滚责任。
- 聚合器检测到已有事务后必须按 S3-T02 现有契约加入，不得嵌套提交。
- 多商品处理中后续商品失败，前面商品的 Batch/Task/Item/Draft 也必须全部回滚。
- 回滚后不得让同一个 DbContext 的 ChangeTracker 保留可被误提交的部分变更；使用现有 EF 能力做最小清理，不创建 UnitOfWork 或补偿框架。
- 不得在生产代码加入仅供测试的故障开关；真实 SQLite 测试应通过合法的约束/输入失败或外层事务回滚验证原子性。

## 必须测试

测试必须使用真实临时 SQLite 数据库和正式 `StoreDbContext`，不得用 EF InMemory provider 代替。至少覆盖：

1. `next_trigger_date > businessDate`：不处理、不改 Batch、不建任务。
2. `next_trigger_date == businessDate`：节点当天立即处理。
3. `TrackingStatus != active`：即使触发日已到也不处理。
4. 多个活动批次中只命中 `next_trigger_date <= businessDate` 的集合。
5. `none -> discount_50`：Batch 阶段和下一触发日正确，建立当前任务。
6. `discount_50 -> discount_20`：复用原 TaskItem 原地升级。
7. `discount_20 -> withdraw`：复用原 TaskItem 原地升级。
8. `withdraw -> expired`：下一触发日变为 null，复用原 TaskItem 原地升级。
9. 离线跨过多个阶段：只保存当天当前阶段，只产生一个当前 Item，不存在中间阶段历史任务。
10. 计算结果为 `none`：更新必要的 Batch 结果但不创建 Task/TaskItem。
11. 同商品多个触发批次：通过 S3-T02 只得到一条开放 ProductTask，各 Item 保留自身阶段，最高阶段正确。
12. 已有开放任务：通过 S3-T02 原地合并/升级，Task ID 不变。
13. 已有有效 Draft 且原 Item 阶段升级：Draft/DraftItem 内容保留，沿用 S3-T02 标记重新确认；AttentionVersion 不变。
14. 相同业务日期和相同输入重复执行：第二次不增加 Task/Item，不污染 Draft，不无意义更新 Batch 时间戳。
15. 多 Batch/多商品处理中发生中途失败：使用新 DbContext 核验 Batch、Task、Item、Draft 数据整体回滚；原 DbContext 不残留可误提交变更。
16. 候选查询的 SQL/执行计划证明过滤在数据库执行并使用 `IX_batches_tracking_status_next_trigger_date`，未全量扫描历史 Batch。
17. 全部自然阶段推进场景断言 `Batch.AttentionVersion` 和 `HandledAttentionVersion` 均不变。
18. 显式 UTC 写入时间戳被校验；用例不读取系统时钟。

允许合并测试数据与断言，避免为每个阶段复制脚手架；但上述行为证据必须清晰可定位。
