## 一、目标与边界

只在 Application 层实现 Stage 4 后台正式排查闭环：

`开放 ProductTask → 重读数据库真实状态 → 校验完整有效 Draft → 必要的超库存确认 → 创建 Inspection/全部 InspectionItem → 更新 HandledAttentionVersion → 0 件批次调用 S3-T06 → Task completed → 删除正常有效 Draft → 单事务提交`

本卡不接 WPF、ViewModel 或 code-behind，不实现 UI/UX Pro Max 视觉、历史编辑或 `InspectionItemRevision` 写入，不修改 Stage 3 状态机、`ConfirmedImportExecutor`、实体、EF Configuration、schema、migration 或依赖。若现有 schema 无法承载本卡语义，立即停止并报告 Sol，不得自行扩表。

## 二、已冻结的提交语义

### 2.1 HandledAttentionVersion

唯一业务语义为：Batch 最近已经通过正式排查处理完成的 AttentionVersion 水位。

- 正式提交成功时，每个当前 Batch 必须以数据库当前事实执行 `HandledAttentionVersion = AttentionVersion`。
- 只能随正式 `Inspection / InspectionItem` 在同一事务内更新；Draft 保存/重新确认、自然阶段推进、S3-T05、S3-T06 均不得更新。
- `AttentionVersion` 本身不变；不得使用页面缓存版本。
- 写入前拒绝 `HandledAttentionVersion < 0` 或 `HandledAttentionVersion > AttentionVersion` 的不一致状态，不新增数据库 CHECK/migration。
- 初始两个版本都可能为 0，因此二者相等不是“已提交”凭证。幂等权威只认 `ProductTask.Status`、正式 `Inspection` 和 `Inspection.TaskId` 唯一约束。

### 2.2 正常提交后的 Draft

- 只对当前开放 Task 且 `IsInvalid == false` 的有效 Draft，在正式提交同一事务内先删除全部 DraftItem，再删除 Draft。
- 不得删除 S3-T04 留下的系统失效 Draft、其他 Task Draft、系统异常痕迹或任何正式历史。
- 提交失败时 Draft/DraftItem 必须完整保留。
- `AlreadySubmitted` 重放不得顺手清理异常残留 Draft；completed + Inspection + 有效 Draft 属于不一致状态，不做隐式修复。

## 三、最小 Application 契约

新增一个职责单一的具体提交用例及必要的最小 request/result records；不得创建接口加单实现、Repository、UnitOfWork、EventBus、Outbox、CQRS、通用提交或 confirmation token 框架。

请求只需包含：

- `TaskId`、`ProductId`。
- 显式 `BusinessDate`。
- 显式 UTC `SubmittedAtUtc`。
- 可空的超库存确认事实：调用方上次确认的 `EffectiveStockQty` 与 `TotalCheckedQty`。

请求不得包含或决定阶段、库存、TaskItem/Batch 提交集合、CheckedQty、检查人或检查日期。返回普通 DTO/record，不暴露 tracked entity、DbSet 或 IQueryable，至少明确表达：

- 首次提交成功及 `InspectionId`。
- `AlreadySubmitted` 及既有 `InspectionId`。
- `RequiresOverStockConfirmation` 及当前 `EffectiveStockQty / TotalCheckedQty`。
- Task/数据不一致、草稿不完整、需重新确认等明确拒绝结果；不得吞异常或把失败伪装为空结果。

## 四、每次 Submit 必须重读数据库

不得相信页面缓存、S4-T01 DTO、S4-T02 readiness 或请求中的业务事实。每次 Submit 都从同一 StoreDbContext/事务重新读取：

- Product、目标 ProductTask、全部当前 ProductTaskItem。
- 每个 Item 对应 Batch 及当前两个版本。
- `RequiresReconfirmation`。
- 当前 Draft 及全部 DraftItem、InspectorName、CheckDate。
- Product 当前 `EffectiveStockQty`。
- 目标 Task 是否已有正式 Inspection。

提交集合以数据库当前 TaskItem 集合为唯一权威；调用方不能选择部分 Batch。

## 五、Task 与幂等门禁

- 首次正式提交只允许 `Task.Status == open` 且 Task/Product 归属匹配。
- Task 不存在或 `system_closed`：拒绝且零写入。
- `completed + Inspection`：返回 `AlreadySubmitted` 和既有 InspectionId，业务图零写入，不重复事件、Batch stop、版本更新、Task完成或 Draft操作。
- `completed + 无 Inspection`：数据不一致，明确拒绝。
- completed + Inspection 异常残留有效 Draft：仍不得隐式清理，应返回/报告不一致。
- SQLite `Inspection.TaskId` 唯一约束继续作为并发与重复提交的最后保护。

## 六、完整草稿与重新确认门禁

当前 Task 每个 TaskItem 都必须存在当前有效 Draft 中的对应 DraftItem，且 `CheckedQty != null`：

- `null`：未完成，禁止提交。
- `0`：合法正式结果。
- `> 0`：合法正式结果。

同时必须满足：

- InspectorName 必填并 Trim，Trim 后为空拒绝。
- Draft.CheckDate 非空且 `CheckDate <= BusinessDate`；不得读取系统日期。
- `SubmittedAtUtc` 必须为 UTC，并满足现有实体/生命周期时序约束；不得增加复杂时间规则。
- 每个 TaskItem 的 `RequiresReconfirmation == false`。
- `DraftItem.ConfirmedAttentionVersion == TaskItem.AttentionVersion == Batch.AttentionVersion`。

任一不满足则整次拒绝且零写入。不得自动 Reconfirm、补版本、清除 RequiresReconfirmation 或修复 TaskItem/Batch 版本不一致。

## 七、阶段与正式快照

- Inspection 阶段快照取数据库当前 Task.HighestStage。
- 每个 InspectionItem 阶段快照取对应 TaskItem 自身 Stage，不得全部覆盖为商品最高阶段。
- 不重新调用或复制 S3-T01 效期算法，不接受调用方阶段。
- Inspection 使用现有字段保存 TaskId、ProductId、商品编码/名称/条码、Task阶段、当前库存、检查人、检查日期和 SubmittedAtUtc 快照。
- 为全部当前 TaskItem 创建 InspectionItem，使用现有字段保存 Product/Batch 归属、生产日期、有效日期、Item实际阶段、当前累计到货、CheckedQty 和时间快照；不得遗漏 0 件 Item。
- 首次提交不创建 InspectionItemRevision。

## 八、库存超量确认

以数据库当前全部非空 CheckedQty 求和得到 `TotalCheckedQty`，与当前 `Product.EffectiveStockQty` 比较：

- `TotalCheckedQty <= EffectiveStockQty`：无需额外确认。
- `TotalCheckedQty > EffectiveStockQty` 且请求未精确确认当前两值：返回 `RequiresOverStockConfirmation` 与当前两值，正式业务图零写入。
- 只有请求确认的库存和合计同时精确等于本次重读/重算事实，才允许继续超库存提交。
- 库存或 Draft 数量变化会使旧确认自动失效，并返回新的当前警告；不得使用永久 `ConfirmOverStock=true`。
- 用户也可先调用 S4-T03 修正库存，再由本卡重新读取并重新判断。

## 九、正式写入与 S3-T06 编排

首次合法提交在一个 SQLite 外层事务内：

1. 创建 1 条 Inspection 和当前 TaskItem 数量对应的全部 InspectionItem。
2. `SaveChanges`，让真实 InspectionId/InspectionItemId 在当前事务可见。
3. 对每个 `CheckedQty == 0` 的真实 InspectionItem 调用既有 `BatchCheckedZeroLifecycleUseCase`，使用同一 StoreDbContext、同一外层事务、本次真实 ID、当前 Product/Batch ID 与合法显式时间。
4. 每个当前 Batch 以数据库当前值设置 `HandledAttentionVersion = AttentionVersion`；AttentionVersion 不变。
5. 将 ProductTask 设置为 canonical `completed`，更新现有完成/更新时间字段；不得删除 Task/TaskItem 或写成 `system_closed`。
6. 先删除当前正常有效 DraftItem，再删除 Draft。
7. 统一 SaveChanges/Commit。

不得自行修改 0 件 Batch 的 TrackingStatus、StopReason、StoppedAtUtc、NextTriggerDate 或创建 `batch_checked_zero` 事件。CheckedQty > 0 的 Batch 除 HandledAttentionVersion 外，不得修改 tracking、到货量、AttentionVersion 或 generation。

## 十、事务、失败与 ChangeTracker

事务所有权沿用已验收的 Stage 3/S4-T03 Application 模式：自有事务统一提交/回滚；若支持加入调用方已有事务，不嵌套提交或回滚调用方事务。不得建设 Repository/UnitOfWork。

任一步失败均须使整个业务图恢复提交前状态，至少覆盖：

1. Inspection insert 后失败。
2. 部分 InspectionItem insert 后失败。
3. HandledAttentionVersion 更新失败。
4. 第一个 0 件 Batch 停止成功、第二个失败。
5. LifecycleEvent 写入失败。
6. ProductTask completed 更新失败。
7. DraftItem 删除失败。
8. Draft 删除失败。
9. 最终 Commit 前失败。

自有事务失败后不得留下可被后续 SaveChanges 误提交的 Added Inspection/Item、Batch 版本/停止变化、Task completed 或 Deleted Draft；ChangeTracker 必须清理或恢复。生产代码不得增加测试故障开关，使用真实 SQLite trigger/约束注入故障。

## 十一、允许的业务图变化

合法成功只允许：

- 新增 1 Inspection、N InspectionItem。
- 当前 Batch.HandledAttentionVersion 更新到当前 AttentionVersion。
- 0 件 Batch 发生 S3-T06 批准的停止状态和对应 LifecycleEvent。
- ProductTask 变为 completed。
- 删除当前正常有效 DraftItem/Draft。

除此之外 Product库存、归零状态、Product/Batch generation、Batch AttentionVersion、正数 Batch tracking、Current/MaxArrivalQty、其他商品、InventoryAdjustment、历史 Inspection 和 InspectionItemRevision 全部逐字段不变。
