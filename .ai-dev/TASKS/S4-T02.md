## 一、目标

只在 Application 层实现当前开放 ProductTask 的草稿写能力：

`部分填写 → 自动保存 → 离开/重启后由 S4-T01 恢复`

以及：

`任务阶段或 AttentionVersion 变化 → 保留原草稿 → 要求重新确认 → 显式确认当前版本`

S4-T01 已提供 Dashboard、开放任务列表、详情和草稿只读 DTO。本卡只负责草稿保存、重新确认、readiness 结果与用户主动清空，不重新建设查询面，不接 WPF。

## 二、开工核验事实

- `drafts.task_id` 唯一，每个 Task 最多一条 Draft，不是“每个 Task 最多一条有效 Draft”。系统失效 Draft 仍占用该 Task 的唯一位置。
- Draft 以 `IsInvalid / InvalidReason / InvalidatedAtUtc` 保存系统失效痕迹；有效 Draft 必须同时满足 `IsInvalid == false` 且失效字段为空。
- DraftItem 以 `(DraftId, TaskItemId)` 唯一，并通过组合外键保证 Draft、TaskItem 属于同一 Task。
- DraftItem.CheckedQty 已由 SQLite CHECK 支持 `null / 0 / 正整数`，负数拒绝。
- DraftItem.ConfirmedAttentionVersion 为非负整数；TaskItem 保存当前 AttentionVersion 与 RequiresReconfirmation。
- S3-T02 在已有有效 Draft 时，阶段升级或 AttentionVersion 增加会保留 Draft/DraftItem，并把对应 TaskItem.RequiresReconfirmation 设为 true；它不会替 Stage 4 自动确认。
- S3-T04 商品归零会把开放 Task 改为 `system_closed`，并将有效 Draft 原地标记失效；S4-T02 不得把它复活或删除。

现有 schema 足以承载 S4-T02。默认不得修改实体、EF Configuration、DbContext、migration 或 ModelSnapshot。若实现发现无法可靠表达已批准语义，立即停止并报告 Sol，不得自行扩表。

## 三、最小 Application 用例

新增一个职责单一的具体 Application 用例，例如 `InspectionDraftUseCase`，并只增加所需最小 request/result record。不得创建接口加单实现、Repository、UnitOfWork、Draft Framework 或通用状态机。

至少提供三个明确动作：

1. SaveDraft：保存或更新当前有效草稿。
2. ReconfirmItem：显式重新确认一个当前 TaskItem。
3. ClearDraft：用户主动清空当前有效草稿。

保存与重新确认必须是不同方法、不同请求和不同状态转换。SaveDraft 绝不能内部调用 ReconfirmItem 或顺带清除 RequiresReconfirmation。

## 四、显式请求事实与时间边界

### 4.1 SaveDraft 请求

最少包含：

- TaskId。
- ProductId。
- 显式 BusinessDate。
- 显式 UTC SavedAtUtc。
- InspectorName，可空。
- CheckDate，可空。
- 本次要保存的零到多个 DraftItem 输入。

每个 DraftItem 输入最少包含：

- TaskItemId。
- BatchId。
- 调用方页面观察到的 AttentionVersion。
- CheckedQty，可空。

同一请求不得包含重复 TaskItemId 或重复 BatchId。ID 必须为正；观察版本不得为负；SavedAtUtc 必须为 UTC。Application 内不得读取 `DateTime.Now`、`DateTime.UtcNow` 或其他系统时钟。

DraftItem 输入是明确 patch：

- 请求中包含该 Item 且 CheckedQty 为 null，表示用户清空该输入。
- 请求未包含某个当前 TaskItem，表示本次不修改其既有 DraftItem，也不自动补行。
- 允许 item 列表为空，以单独保存或清空检查人/检查日期。

### 4.2 ReconfirmItem 请求

最少包含：

- TaskId。
- ProductId。
- TaskItemId。
- BatchId。
- 调用方明确确认的 AttentionVersion。
- 显式 UTC ConfirmedAtUtc。

### 4.3 ClearDraft 请求

最少包含 TaskId 与 ProductId。清空只删除当前有效草稿，不需要创造清空时间或审计事件。

## 五、草稿允许不完整

自动保存允许：

- 只填写部分 Batch。
- 其他 Batch 没有 DraftItem，或 DraftItem.CheckedQty 为 null。
- InspectorName 为空。
- CheckDate 为空。

CheckedQty 语义必须保持：

- null：尚未填写。
- 0：已检查，现场没有该批次。
- 正整数：已检查并存在对应数量。

不得把 null 转换成 0。负数必须在任何写入前拒绝。

“所有当前待排查批次必须填写、检查人和检查日期完整”是 S4-T04 正式提交门禁；S4-T02 不得因为草稿不完整而拒绝保存。

## 六、每次写入前重新读取当前 Task

SaveDraft、ReconfirmItem、ClearDraft 每次都必须从数据库重新读取：

- ProductTask 是否存在。
- Task.Status 是否仍为 `open`。
- Task.ProductId 是否匹配请求 ProductId。
- 当前 TaskItem 集合。
- 目标 TaskItem、Batch 与 Product 的组合归属。
- 当前 TaskItem.AttentionVersion。
- 当前 Batch.AttentionVersion。
- 当前 TaskItem.RequiresReconfirmation。
- 当前 Draft 是否存在、是否有效及其 DraftItem。

不得相信 S4-T01 页面缓存或请求中传入的阶段、库存、任务状态和确认状态。

SaveDraft 和 ReconfirmItem 若发现数据库当前 TaskItem.AttentionVersion 与对应 Batch.AttentionVersion 不一致，必须拒绝且不得在本卡内修复。

Task 不存在、`completed` 或 `system_closed` 时，三个动作都不得创建、更新、确认或删除可编辑草稿。特别是 S3-T04 已系统关闭 Task 后，旧页面 SaveDraft 不得“复活” Draft。

## 七、只接受当前 TaskItem

SaveDraft 和 ReconfirmItem 只接受当前开放 Task 中真实存在的 TaskItem。必须验证：

- TaskItemId 属于当前 Task。
- BatchId 与该 TaskItem 的 BatchId 完全一致。
- TaskItem.ProductId、Batch.ProductId 与 Task.ProductId 完全一致。

禁止给其他商品 Batch、正常但不属于当前 Task 的 Batch、其他 Task 的 Item 或任意构造 BatchId 写草稿或确认。

如果页面观察版本大于当前 TaskItem/Batch 版本，属于非法未来事实，拒绝。SaveDraft 允许观察版本小于当前版本，以安全保留陈旧页面输入，但不得因此改变当前确认状态。

## 八、检查人和检查日期

一个 Draft 只保存一个 InspectorName：

- null 或全空白统一保存为 null。
- 非空值 Trim 后保存。
- 不建设员工账号、人员表或最近人员设置。

CheckDate 可空；非空时必须 `CheckDate <= BusinessDate`。未来日期在写入前拒绝。

BusinessDate 只用于草稿日期校验。未来 WPF 默认当天属于 UI 行为，本卡不实现。

## 九、唯一 Draft 与幂等保存

SaveDraft：

- 当前没有任何 Draft：创建一条有效 Draft。
- 已有有效 Draft：原地更新。
- 已有失效 Draft：拒绝，不重新激活、不覆盖、不创建第二条。
- 同一 Task 不创建重复 Draft。
- 同一 Draft/TaskItem 不创建重复 DraftItem。

首次创建 Draft 时显式写入 CreatedAtUtc/UpdatedAtUtc = SavedAtUtc。只有 InspectorName、CheckDate、DraftItem CheckedQty 或新 DraftItem 实际变化时，才把 Draft.UpdatedAtUtc 更新为 SavedAtUtc。

相同规范化内容重复保存必须返回无变化结果，并保持：

- Draft/DraftItem 数量不变。
- Draft.CreatedAtUtc/UpdatedAtUtc 不变。
- DraftItem.ConfirmedAttentionVersion 不变。
- TaskItem.RequiresReconfirmation 与 UpdatedAtUtc 不变。

## 十、保存不得执行重新确认

SaveDraft 只保存用户输入：

- 已存在 DraftItem 时，只在请求明确包含时更新 CheckedQty；保留原 ConfirmedAttentionVersion。
- 新建 DraftItem 时，ConfirmedAttentionVersion 使用调用方观察到的非负 AttentionVersion，作为该输入关联的观察版本。
- 无论请求观察版本是否等于当前版本，SaveDraft 都不得把 TaskItem.RequiresReconfirmation 从 true 清为 false。
- SaveDraft 不修改 TaskItem.AttentionVersion、Stage、RequiresReconfirmation、CreatedAtUtc 或 UpdatedAtUtc。

这允许陈旧页面安全保存用户草稿值，同时保证它不能把 v1 错误确认成 v2。自然阶段升级可能不改变 AttentionVersion，因此是否仍需确认只认 TaskItem.RequiresReconfirmation，不从版本差重新推导。

## 十一、显式重新确认

ReconfirmItem 只有在以下数据库当前事实全部成立时才可成功：

- Task 当前仍为 open，Product 归属匹配。
- TaskItem 当前仍存在且 Batch/Product 归属匹配。
- 当前有效 Draft 与对应 DraftItem 已存在。
- DraftItem.CheckedQty 非 null。
- 请求 AttentionVersion 与当前 TaskItem.AttentionVersion 完全一致。
- 请求 AttentionVersion 与当前 Batch.AttentionVersion 完全一致。
- TaskItem.RequiresReconfirmation 当前为 true。

成功后在同一事务中：

- DraftItem.ConfirmedAttentionVersion = 当前 AttentionVersion。
- TaskItem.RequiresReconfirmation = false。
- TaskItem.UpdatedAtUtc = ConfirmedAtUtc。
- Draft.UpdatedAtUtc = ConfirmedAtUtc。

普通 SaveDraft 永远不得产生上述状态转换。

若页面打开后再次发生新到货或其他 S3-T02 变更，旧请求版本与当前版本不同，必须在写入前拒绝；DraftItem、TaskItem 和 Draft 时间戳全部保持不变。

对已经完成相同当前版本确认的精确重放，可返回明确的无变化结果；只有在 `RequiresReconfirmation == false` 且 DraftItem.ConfirmedAttentionVersion 与当前 TaskItem/Batch AttentionVersion 完全一致时才是合法幂等重放。其他“不需确认但版本不一致”属于不一致状态，拒绝且不修复。

## 十二、轻量 readiness 结果

SaveDraft 与 ReconfirmItem 成功后可返回基于本次事务内当前事实计算的轻量结果：

- CurrentItemCount。
- FilledItemCount：当前 TaskItem 中存在 DraftItem 且 CheckedQty 非 null 的数量。
- MissingItemCount。
- RequiresReconfirmationCount。
- HasInspectorName。
- HasCheckDate。
- AllItemsFilled。
- IsDraftComplete：全部当前 Item 已填写、检查人非空、检查日期非空且仍需重新确认数量为 0。

该结果只供后续 UI 提示。S4-T04 仍必须重新读取数据库并独立执行全部正式提交门禁；不得把 IsDraftComplete 当作提交授权令牌。

## 十三、用户主动清空草稿

现有 schema 对每 Task 只有一条 Draft，且失效 Draft 是 S3-T04 必须保留的系统痕迹。因此本卡固定最小方案：

- Task 当前仍 open 且没有 Draft：返回无变化，不创建记录。
- Task 当前仍 open 且 Draft 有效：在一个事务中先删除其 DraftItem，再删除 Draft。
- Draft.IsInvalid 为 true：明确拒绝，绝不重新激活、覆盖或物理删除。
- Task 已 completed/system_closed：明确拒绝，不删除其旧 Draft。

清空不得删除 Inspection/InspectionItem，不修改 ProductTask/TaskItem，不修改 Product/Batch，不写 LifecycleEvent。

本卡的用户主动清空方案不决定 S4-T04 正式提交后的 Draft 处置。D-016 的 S4-T04 前专项治理门禁保持不变。

## 十四、事务、故障和 DbContext 状态

SaveDraft、ReconfirmItem、ClearDraft 各自必须拥有清晰的真实 SQLite 事务：

- 一次操作的全部 Draft、DraftItem 和允许的 TaskItem 变化统一提交。
- 任一步失败全部回滚。
- 失败后不得留下可被调用方误提交的半状态；ChangeTracker 必须清理或恢复到调用前语义。

不得出现：

- 只保存部分 DraftItem。
- ConfirmedAttentionVersion 已更新但 RequiresReconfirmation 未清除。
- RequiresReconfirmation 已清除但 DraftItem 仍是旧确认版本。
- Draft/TaskItem 时间戳半更新。
- 清空只删 DraftItem 或只删 Draft。

使用真实 SQLite 保存/确认故障注入证明回滚。不创建 Repository、UnitOfWork、补偿队列或后台重试。

## 十五、陈旧页面重点场景

必须证明：

`页面读取 v1 → 后台新增到货使 AttentionVersion=v2 且 RequiresReconfirmation=true → 旧页面继续 SaveDraft(v1)`

结果：

- 请求中的用户 CheckedQty 可安全保存。
- 已有 DraftItem.ConfirmedAttentionVersion 不被普通保存推进；新 DraftItem 只记录请求观察版本 v1。
- TaskItem 当前 AttentionVersion 仍为 v2。
- RequiresReconfirmation 仍为 true。
- 旧页面 ReconfirmItem(v1) 被拒绝且无写入。
- 只有 ReconfirmItem(v2) 且 Batch/TaskItem 当前版本都为 v2 时才允许清除。

阶段升级但 AttentionVersion 不变时也必须依赖 RequiresReconfirmation 保持门禁，并允许基于当前版本执行显式重新确认。
