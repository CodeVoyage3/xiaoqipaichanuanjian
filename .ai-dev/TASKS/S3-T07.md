## 开工前已核验的仓库事实

### ConfirmedImportExecutor 事务

- 当前 `ConfirmedImportExecutor.Execute` 验证文件、创建导入前 SQLite 快照后，无条件 `BeginTransaction`，在内部写 Import、Product/Batch、Issue、Workbook、BackupRecord 和 Workbook 保留裁剪，随后 Clear tracker 并 Commit。
- S3-T04 与 S3-T05 已支持项目统一模式：无当前事务时自行拥有；存在外层事务时加入且不抢先 commit/rollback。
- 因此原子组合不需要重写 Stage 2 持久化规则。只需把 ConfirmedImportExecutor 的事务拥有方式机械收窄为同一模式：当前无事务才创建/提交/回滚/释放自己的事务；当前已有事务时只执行既有持久化并返回，由外层编排器决定最终 commit/rollback。
- 该修改不得改变任何契约验证、陈旧计划验证、字段应用、Workbook/Backup、Issue、保留两份、结果代码或直接调用行为。不得把任何 S3-T01～T06 引用或规则加入 ConfirmedImportExecutor。
- 外层模式下 Executor 失败仍返回既有失败结果；外层编排器必须立即回滚。Executor 不得擅自提交或回滚调用方事务。

这属于最小事务组合能力，不是“实质重构 Stage 2”。若实现中必须拆改其业务规则或改变直接调用语义，立即停止并报告 Sol。

### ImportPlan 显式事实缺口

- `NewBatchPlan` 明确新键；`BatchUpdatePlan.FieldChanges` 明确 before/after；`BatchUnchangedPlan` 保存完整批次值。编排器可在 Executor 前按计划涉及的唯一键定向读取 pre-import Batch，冻结 Id、PreviousMaxArrivalQty 和 AttentionVersion，再应用已有 FieldChanges 得到明确 after；这不是重算 diff，也不得查询未出现批次。
- Planner 已有 `StockDecision.IsValid/Quantity`，但 `ImportPlan` 当前未保留“库存合法且显式出现”的事实。特别是既有库存本来为 0、Excel 仍明确为 0 时不会产生字段变化；导入后数据库值本身无法证明本次明确 0。Stock conflict、空白和非法值也不得被猜成 0。
- 本卡允许 Planner/ImportPlan 增加一个最小只读集合，例如 `ExplicitProductStocks(ProductCode, Quantity)`：只收录本次 Excel 已出现、无冲突、合法解析的非负库存。它直接来自现有 StockDecision，不新增库存规则，不改变 Stage 2 预览或持久化结果。
- ConfirmedImportExecutor 只需对该只读事实做最小形状/陈旧性一致性验证（如任务实现确有必要），不得消费它执行 Stage 3。
- 不允许重新解析 Workbook、不重新分类、不新增第二份 diff、也不得从导入后 Product.EffectiveStockQty 反推“本次明确 0”。

## 一、确认导入后的原子编排入口

新增一个职责单一的具体 Application 编排器，例如 `ConfirmedImportLifecycleOrchestrator`；不增加单实现接口、工作流框架或 Service 容器。

输入最少包含：

- 已冻结的 `ImportConfirmationContract`。
- StoreDbContext。
- snapshot directory。
- 显式 `ParsedAtUtc`。
- 显式 `BusinessDate`，供 S3-T05/S3-T01 计算。

编排顺序：

1. 在任何写入前，只按 ImportPlan 明确商品/批次键定向读取 pre-import 状态，冻结本次后置事实：existing Batch Id/previous max/current after/expected+target AttentionVersion，以及明确 new 键和显式合法库存事实。
2. 打开一个外层 SQLite 事务。
3. 调用现有 ConfirmedImportExecutor；它加入当前事务并执行全部 Stage 2 持久化。
4. 若 Stage 2 返回失败，外层立即回滚、清理 tracker，并原样返回失败；不得执行 Stage 3。
5. 使用返回 ImportId 在当前事务内定向解析本次 ProductId/BatchId，并验证 LastSeenImportId、唯一键、after 值与冻结事实一致。
6. 按本次明确 Product 分组执行批准优先级：
   - 显式合法库存事实为 0：先确保 Stage 2 已持久化当前库存并 SaveChanges，然后只调用 S3-T04 `ProductStockZeroLifecycleUseCase`，SourceImportId 使用本次 Import；该商品绝不调用 S3-T05。
   - 显式合法库存为正，或本次没有合法库存事实但 Stage 2 沿用后的 Product 当前有效库存为正：只把 ImportPlan 明确涉及且合法的 Batch 冻结事实交给 S3-T05。
   - 本次没有合法库存事实且当前库存为 0：两者均不调用；不得把缺失/空白/非法/冲突解释为明确 0，S3-T05 也不得被错误调用到 0 商品。
7. S3-T05 输入必须使用 Executor 前冻结的 previous max/expected AttentionVersion 和 ImportPlan 明确 after/new 事实；不得从导入后 `CurrentArrivalQty == MaxArrivalQty` 猜真正新增到货。
8. 所有 Product 处理成功后统一 commit；任一 S3-T04/S3-T05/Task/Draft/Event/约束失败，统一 rollback，并返回明确失败结果。

最终禁止出现数据库中的 `Succeeded Import` 已提交但该次必需 Stage 3 状态永久缺失。失败后新 Import、Product/Batch 导入变更、Workbook/BackupRecord/Issue/裁剪和全部 Stage 3 状态都必须回到导入前数据库事实。已发布的导入前快照文件可作为失败恢复痕迹保留，不得伪装成成功 Import。

## 二、商品归零优先级

对同一商品只允许以下二选一：

- 本次显式合法库存为 0：调用 S3-T04；新 Batch 也作为该商品全部 Batch 被停止，S3-T05 完全不调用，不增加 AttentionVersion、不恢复、不创建阶段任务。
- 非明确 0 且当前有效库存为正：调用 S3-T05 处理明确 new/existing facts。

必须通过编排结果证明优先级，不得依赖 S3-T05 自己拒绝 0 商品“碰巧兜底”。Stock conflict 不产生显式库存事实，沿用 Stage 2 既有库存结果；本次未出现的 Product/Batch 不进入查询或调用集合。

## 三、启动运行编排与时钟回拨

新增一个最小 Application 运行编排器，例如 `ApplicationStartupCoordinator`，输入 StoreDbContext、显式 `BusinessDate today` 与显式 UTC `OccurredAtUtc`。

流程必须在一个明确事务中：

1. 按主键读取唯一 `AppState(Id=1)`；缺失或重复属于数据库异常，不自行补造第二状态源。
2. 若 `LastNormalRunDate.HasValue && today < LastNormalRunDate`：不调用 S3-T03，不修改 Batch/Task/Draft/AppState，返回明确 clock-rollback 结果供入口记录 warning。
3. 否则调用现有 `StartupRecalculationUseCase.Execute(context, today, occurredAtUtc)`；它加入外层事务并继续只查 `active + next_trigger_date <= today`。
4. S3-T03 成功后将 `LastNormalRunDate = today`（相同日期保持幂等），SaveChanges 后统一 commit。
5. S3-T03 或 AppState 更新失败时全部 rollback，Batch/Task/Item/Draft 与 LastNormalRunDate 均不留下半状态。

不得在该 Coordinator、S3-T03 或 Domain 读取系统时间，不得重新实现阶段计算、查询或任务聚合。
