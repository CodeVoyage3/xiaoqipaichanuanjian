在不引入真实业务 Schema 变化的前提下，为未来 migration 9→10→11… 建立可验证、可恢复、fail-closed 的跨 Schema 在线升级保护，使以下情况成立：

> 新版本开始修改数据库 Schema 后，只要候选程序尚未被正式提交为成功版本，任何启动失败、迁移失败、崩溃、断电/硬杀、健康检查失败或程序树回滚，都不得让旧程序直接面对已升级后的数据库；必须先恢复升级前一致性数据库快照，再恢复并启动旧程序。

## 四、跨 Schema 许可规则

沿用 S9-T04 已签名 `update-manifest.json`：`targetMigrations` 为目标完整有序 migration 列表，`source` 给出允许来源版本/migration 范围。签名与完整包 hash 仍为前置门禁，不因本卡放宽。

在任何 Schema 写入前必须同时确认：

1. 当前实际数据库 migration 历史可读、完整、无未知/重复/分叉。
2. 当前实际 migration 列表与候选声明均经过独立身份校验。
3. 跨 Schema 时，**当前实际 migration 列表必须是目标 `targetMigrations` 的严格前缀**；只允许向前追加，不允许删除、重排、分叉或 Down migration。
4. 当前版本必须位于 manifest 的 source version/migration 许可范围。
5. 候选程序树、版本、RID、manifest、package SHA/bytes、完整 tree fingerprint 均与已验证包一致。
6. 任一不满足即在数据库变化前 fail-closed。

同 Schema 升级继续走现有安全路径，不因本卡降低 S9-T05/S9-T06 已有门禁。

## 五、升级前数据库保护快照

跨 Schema 升级不得依赖“迁移失败后执行 Down migration”恢复。唯一允许的旧 Schema 恢复来源是**迁移前保护快照**。

保护快照必须：

- 在旧主程序进入 maintenance、所有权威业务写结束、Reminder/background 停止后建立。
- 明确关闭/释放 SQLite 连接并处理 WAL/SHM 一致性；不得把未知、外来或未解析 sidecar 静默并入快照。
- 优先复用 Stage8 已验收的保护快照/恢复安全能力；任何复用必须保留来源身份、fingerprint、integrity、foreign_keys、migration 历史和防外来 WAL 规则。
- 快照与 operationId、source version、source migration 完整列表、数据库逻辑 fingerprint、创建时间、受控 data root 身份绑定。
- 快照创建/验证失败时，**不得启动候选迁移，不得切换成需要新 Schema 的候选**。
- 快照必须位于 data root 下受控、不可由网络/用户参数任意指定的升级恢复区域；拒绝 reparse/junction/symlink/UNC/path traversal/ADS。
- 不修改用户已有普通 Backup 的保留策略；升级保护快照属于事务恢复证据，不冒充普通用户备份。

若未来迁移会修改 SQLite 之外的持久业务状态，必须先扩展受保护持久集并另行验收；本卡当前仅覆盖现有 Schema 迁移实际触达的受控 SQLite 数据库及必要一致性 sidecar/元数据。

## 六、跨 Schema 事务状态机

在 S9-T05 journal 基础上增加可恢复的 Schema 事务证据，至少能表达等价状态：

`SchemaSourceVerified → SchemaSnapshotPreparing → SchemaSnapshotVerified → SchemaMigrationAuthorized → SchemaMigrationStarted → SchemaMigrationApplied → SchemaHealthVerified → CandidateCommitted`

以及失败恢复：

`RollbackRequired → CandidateStopped → OldAppRestored → SchemaSnapshotRestoreStarted → SchemaSnapshotRestored → OldSchemaVerified → OldCandidateHealthVerified → RolledBack`

要求：

- 阶段单向、持久、安全写入；每一步都绑定 operationId 和程序树/数据库身份。
- 不能仅靠“文件存在/目录存在/数据库能打开”推断阶段。
- `SchemaMigrationStarted` 之后、`CandidateCommitted` 之前发生任何无法证明安全续跑的中断，默认进入回滚路径。
- 旧程序在数据库恢复到 source migration 并通过完整健康检查之前，**绝不允许启动**。
- candidate 通过 health ACK 后才允许提交；ACK 必须包含 target version、PID/start time、target migration 完整列表、integrity/FK、核心只读、UI loaded。
- ACK 前除受控 EF migration 和升级健康检查外，禁止普通 Import/Task/History/Reminder/Backup/Restore 等业务写。
- 若已经 `CandidateCommitted`，重启恢复必须验证提交证据后完成收尾，不因 journal 未写 Completed 就盲目恢复旧 Schema。

## 七、迁移失败与恢复原则

任何 migration 异常、candidate 崩溃、ACK timeout、版本/迁移不匹配、integrity/FK/core read/UI health 失败，都必须：

1. 阻止 candidate 继续业务写并确认退出。
2. 按既有程序树规则恢复完整 old app。
3. 从本 operation 的保护快照恢复旧 Schema 数据库。
4. 核对 migration 完整列表恢复为 source；integrity/FK/核心数据 fingerprint 满足验收。
5. 才允许启动 old app 并等待旧版 health ACK。
6. 程序树或数据库任一恢复失败，进入 `FailedNeedsManualRecovery`，保留 old/candidate/snapshot/journal/诊断证据，绝不伪报 RolledBack，绝不让旧版直接打开不兼容数据库。

不得以固定 `Thread.Sleep`、无限重试、删除 journal、删除旧程序或跳过数据库校验换取绿色。

## 八、测试实现方式：禁止真实 migration10

生产仓库 migration 必须保持 9。本卡用**测试专用跨 Schema fixture**验证机制：

- source fixture 等价 migration9。
- target fixture 在隔离测试工程中模拟严格前缀追加的 migration10/11，包含真实 SQLite DDL/DML 变化与可核对数据。
- fixture 不进入正式 App publish、Release ZIP、Setup，不改变生产 ModelSnapshot，不成为 EF 正式 migration。
- 至少包含有 BLOB、历史、设置等代表性合成数据的前后 fingerprint，证明成功迁移保数据、失败回滚恢复原值。

必须另有实际 WPF/Updater 隔离事务，证明生产升级编排、maintenance、候选 health 模式和 rollback 接线真实走通；不能只用纯单元测试模拟状态机。

## 九、最低验收矩阵

至少覆盖：

A. 同 Schema 9→9 回归不退化。
B. 合成 9→10 正常迁移、候选 ACK、提交成功。
C. 9→10 migration 中途抛异常，恢复旧 app + migration9 DB。
D. migration 已落库但 ACK 前 candidate 崩溃，恢复 migration9。
E. migration 后 integrity/FK/core read/UI health 失败回滚。
F. 保护快照创建失败，在 migration 前安全阻断。
G. 保护快照验证/hash/fingerprint 被篡改，禁止使用并进入安全失败。
H. source migration 不在 manifest 范围，阻断。
I. target migration 非 source 严格前缀追加（删除/重排/分叉），阻断。
J. candidate 静态 migration 声明与 signed manifest 不符，阻断。
K. 外来/错配 WAL/SHM，不得被错误接受为安全 source snapshot。
L. app 恢复成功但 DB 恢复失败 → `FailedNeedsManualRecovery`，旧 app 不启动。
M. DB 恢复成功但 old tree 恢复失败 → `FailedNeedsManualRecovery`。
N. 双 Updater/双 operation 互斥。
O. 受控 IOException/AccessDenied/SharingViolation，不无限重试。
P. reparse/junction/symlink/UNC/path traversal/ADS 全部 fail-closed。
Q. candidate committed 后、Completed 前硬杀，重启不得误回滚已提交成功事务。
R. rollback 恢复后旧版真实 health ACK，migration/source fingerprint 正确。

硬 Kill/重启至少覆盖：snapshot 已建前后、migration 开始前、migration DDL/DML 中代表点、migration 已完成 ACK 前、ACK 后 commit 前、old app 恢复后 DB restore 前/中/后、旧版 ACK 前。每个关键阶段应有稳定可重复证据，不允许失败后无限重跑挑绿色样本。
