## 目标

建立一个独立、可复用的 Application 层商品任务聚合能力：消费调用方已经明确给出的单个商品及其一组批次当前阶段、关注版本和重新确认要求，将需要排查的批次聚合到该商品唯一开放 `ProductTask`。

本卡只负责：

`显式批次结果 → 商品唯一开放任务及任务项`

本卡不判断批次结果为何产生。后续 S3-T03、S3-T04、S3-T05 必须复用本卡的聚合能力，不得各自复制 ProductTask 生成/升级规则。

## 当前仓库事实与正式命名

- 用户需求中的 `HighestPhase` 对应现有 `ProductTask.HighestStage` / SQLite `highest_stage`；不得新增 `HighestPhase`。
- 用户需求中的 `TaskBatchItem` 对应现有 `ProductTaskItem` / SQLite `task_items`；不得新增平行实体或表。
- `ProductTask` 已有 `Status`、`HighestStage`、创建/更新时间和关闭字段。
- `ProductTaskItem` 已有 `TaskId`、`BatchId`、`ProductId`、`Stage`、`AttentionVersion`、`RequiresReconfirmation` 和创建/更新时间。
- `Batch.AttentionVersion` 是批次当前关注版本；`ProductTaskItem.AttentionVersion` 表达任务项当前采用的批次关注版本。
- `InspectionDraftItem.ConfirmedAttentionVersion` 保存草稿项上次确认的任务项版本；版本或阶段变化时不得把它同步覆盖为新版本，否则会伪造用户已重新确认。
- SQLite 部分唯一索引 `IX_tasks_product_id_open` 已保证每商品最多一条开放任务；`IX_task_items_task_id_batch_id` 已保证同一任务内同一批次最多一个任务项。
- S3-T01 已固定 canonical 阶段代码：`none / discount_50 / discount_20 / withdraw / expired`。
- 当前 schema、实体、配置和索引足以承载本卡，默认不得新增 migration 或修改实体。

## 输入契约

一次调用只处理一个明确商品，至少包含：

- `ProductId`。
- 一组普通内存批次结果，每项包含：
  - `BatchId`。
  - `Stage`。
  - `AttentionVersion`。
  - 调用方明确给出的 `RequiresReconfirmation` 或等价布尔要求。
- 用于实际写入时间戳的明确 UTC 时间，或等价的最小可测试时钟入口；不得新增时钟接口加单实现。

输入必须在写库前完成整体校验：

- Product 必须存在。
- 每个 Batch 必须存在且属于本次 Product。
- 同一次调用中 `BatchId` 必须唯一；不得静默接受相互冲突的重复结果。
- `Stage` 只允许 S3-T01 canonical 五值。
- `AttentionVersion >= 0`，并且必须与当前 `Batch.AttentionVersion` 一致；本卡只消费版本，不修改 Batch 版本。
- 缺失商品/批次、跨商品批次、非法阶段、负版本、版本与 Batch 不一致或同批次重复输入时，整次拒绝且不得产生任何写入。

生产结果应为普通内存 DTO，至少能表达是否发生变化、开放 Task Id、最终 `HighestStage`、新增/更新 Item 数；不得返回可由调用方继续保存的 tracked EF 实体。

## 唯一阶段优先级

唯一优先级顺序：

`expired > withdraw > discount_20 > discount_50`

`none` 表示正常，不是待排查阶段，不进入 TaskItem。

要求：

- 阶段优先级必须只有一个生产权威实现。
- Application 聚合器必须调用该权威实现，不得自己复制 `switch`、if/else 或映射表。
- 不得用字符串字典序比较。
- 优先级实现可最小扩展 S3-T01 已有纯 Domain 阶段能力，或新增一个职责单一的纯 Domain helper；不得复制日期/保质期计算，不得建立通用规则引擎、策略集合或配置系统。
- canonical 字符串仍只复用 S3-T01 已有常量；不得再定义一套阶段代码。

纯逻辑测试必须证明四个待排查阶段完整有序、`none` 不可形成任务项、非法代码被拒绝，并证明 Application 实际复用该唯一实现。

## 商品任务聚合规则

### 1. 没有开放任务

- 输入中至少一个批次处于待排查阶段时，创建一条 `Status = open` 的 ProductTask。
- 为每个待排查批次创建一个 ProductTaskItem；每项保留自己的实际 Stage 和 AttentionVersion。
- ProductTask.HighestStage 等于所有新任务项中的最高优先级阶段。
- 输入全部为 `none` 时不创建 Task 或 TaskItem。
- 既有已关闭历史任务不阻止创建新的唯一开放任务，也不得被修改或复用。

### 2. 已有开放任务

- 必须复用现有开放 ProductTask，不创建第二条。
- 新触发批次加入该任务；已有 `(TaskId, BatchId)` 不重复插入。
- 应用本次变化后，必须从该开放任务的全部现有 TaskItem 重新计算正确 HighestStage，不能只看本次输入。
- 新批次阶段低于已有最高阶段时，商品 HighestStage 不得降低。
- 新批次阶段高于已有最高阶段时，原任务原地升级。
- 不修改已关闭历史任务。

### 3. 已有任务项

- 相同批次、相同 Stage、相同 AttentionVersion 且本次没有新的重确认要求：完全幂等，不更新 Item/Task/Draft 时间戳或字段。
- 相同批次进入更高阶段：更新原 ProductTaskItem.Stage，不创建重复项；随后从全部 Item 重算 HighestStage。
- AttentionVersion 增大：更新原 ProductTaskItem.AttentionVersion，不创建重复项。
- 调用方显式要求重新确认：把原 Item.RequiresReconfirmation 设为 true；已经为 true 时保持，不重复污染。
- `RequiresReconfirmation` 在本卡中只能由 false 变 true，不得由重复输入或 false 请求清除；正式重新确认后的清除属于后续提交用例。
- 已有 Item 收到更低 Stage 或更低 AttentionVersion 属于过期/降级输入，本卡必须保守拒绝整次聚合，不得降级、部分应用或静默覆盖。日期回拨和停止/移除规则属于后续卡。
- 对已有 Item 输入 `none` 不删除、不降级、不关闭任务；本卡将其视为无待排查新增动作。批次停止、任务项移除或任务关闭不属于 S3-T02。

### 4. 多批次保持各自阶段

例如同商品三个批次分别为 `discount_50`、`discount_20`、`withdraw`：

- 只存在一条开放 ProductTask。
- 存在三个 ProductTaskItem。
- ProductTask.HighestStage 为 `withdraw`。
- 三个 Item.Stage 仍分别为 `discount_50`、`discount_20`、`withdraw`，不得统一覆盖成最高阶段。

## Draft 与重新确认

本卡不创建、删除、失效或替换 Draft，也不创建第二份 Draft。

当开放任务已有有效 Draft 时：

- 已有 Item 阶段升级必须将该 Item.RequiresReconfirmation 设为 true。
- 已有 Item AttentionVersion 增大必须将该 Item.RequiresReconfirmation 设为 true。
- 调用方显式传入重新确认要求时，相关 Item.RequiresReconfirmation 必须为 true。
- 新批次加入已有任务时，按调用方显式重新确认要求设置新 Item；不得自行判断累计到货或其他原因。
- Draft 的 InspectorName、CheckDate、IsInvalid、InvalidReason、InvalidatedAtUtc、CreatedAtUtc、UpdatedAtUtc 均保持不变。
- 已有 DraftItem 的 CheckedQty 和 ConfirmedAttentionVersion 均保持不变；旧确认版本与新 TaskItem.AttentionVersion 的差异必须保留，供后续提交前识别。
- 完全相同阶段、版本且没有新重确认要求的重复调用，不得改动 Draft、DraftItem 或 RequiresReconfirmation。

无有效 Draft 时，阶段/版本变化只更新任务事实；调用方显式传入 RequiresReconfirmation=true 时仍按输入落到 TaskItem。不得为了未来 UI 创建空 Draft。

已失效 Draft 是历史事实，本卡不得恢复或修改。

## 事务与可复用边界

一次商品聚合中的 ProductTask、全部 ProductTaskItem、HighestStage 和重新确认标记必须原子提交。

要求：

- 没有外层事务时，本用例必须拥有清晰的 SQLite 事务并在成功后提交、失败时回滚。
- 已有调用方事务时，聚合逻辑必须能够参与同一个 StoreDbContext/事务，不得另开第二个 DbContext、提前提交调用方事务或形成嵌套独立业务提交；这是后续 S3-T03/T04/T05 复用本卡的必要条件。
- 可用一个具体聚合器通过最小的事务参与方式实现；不得为此新增 Repository、UnitOfWork 或接口加单实现。
- 任一输入无效或任一 SQLite 写入失败时，Task、Item、HighestStage 和重确认标记均不得部分持久化。
- 测试应使用真实 SQLite 故障触发器或等价数据库故障证明中途失败整次回滚；不得向生产代码加入测试故障开关。
- Application 业务规则本身必须正确查询/复用开放任务；SQLite 开放唯一索引继续作为并发和数据完整性的最后保护。
- 完全幂等调用不得调用无意义 SaveChanges 造成更新时间或 ChangeTracker 污染。
