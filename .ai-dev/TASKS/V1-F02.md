## 5. StageEffectiveDate 与 ReminderDate 精确计算

必须在 Domain/Application 的单一纯计算权威中复用 V1 policy 阈值，不得在 Reminder 查询、WPF 或通知格式中复制阈值。

对合法 `policy_code / policy_version=1` 和批次总效期：

- `discount_50` 的 `StageEffectiveDate = ExpiryDate - 第一阶段阈值`；
- `discount_20` 的 `StageEffectiveDate = ExpiryDate - 第二阶段阈值`；
- `withdraw` 的 `StageEffectiveDate = ExpiryDate - 第三阶段阈值`；
- `expired` 的 `StageEffectiveDate = ExpiryDate`；
- 每个节点的 `ReminderDate = StageEffectiveDate.AddDays(-3)`。

阈值必须与 `ExpiryPolicyCalculator` 完全一致：

- `food_expiry/1`：总效期 `<=270` 天为 `30/14/7`，否则 `90/60/14`；
- `pet_expiry/1`：`90/60/14`；
- `general_long_expiry/1`：仅总效期 `>180` 天，`180/90/14`；
- D/M/Y 总效期换算继续为 `D=value`、`M=value*30`、`Y=value*365`；到期当天为 expired。

建议最小实现是由 `ExpiryPolicyCalculator` 暴露同一组已验证节点日期，现有 `Calculate` 与预提醒共同消费；不得维护第二份 policy switch。

## 6. 预提醒候选资格与跨日行为

预提醒节点在且仅在以下窗口内成为当天候选：

`ReminderDate <= BusinessDate && BusinessDate < StageEffectiveDate`

并同时满足：

- Product 为 Managed；
- policy 是批准值且 version=1；
- 存在 `ScopeKey == CategoryCode`、policy code/version 全匹配且已完成的 ScopeBaseline；
- Product 有效库存大于 0；
- Batch 为 active；
- policy 可计算且批次身份合法。

行为冻结：

- ReminderDate 当天在配置时间前启动：scheduler 到点后提醒；配置时间后启动：启动 scheduler 的首次检查立即按现有 due 语义提醒。
- ReminderDate 当天未运行：后续日期启动时，只要仍满足 `BusinessDate < StageEffectiveDate`，该节点进入当天集中提醒；这是现有“开放候选跨日可再次提醒”的直接复用。
- 跨日补提醒不是持久化一次性补发：在正式节点到达前，该节点每天都可进入当天集中提醒；每个自然日仍最多弹一次。
- `BusinessDate >= StageEffectiveDate` 时，该节点预提醒立即失效；即使软件错过 ReminderDate，也不得在正式 Stage 到达后补发“提前提醒”。
- 日期回拨时继续由 `LastReminderDate > BusinessDate` 返回 `clock_rollback`，不得绕过或回退登记日期。
- 通知失败不登记，当天按现有 scheduler 15 分钟重试；成功后同日不重复。

## 7. 节点身份、商品多批次与集中展示

### 7.1 独立识别与去重

- 单个预提醒节点身份固定为 `(BatchId, TargetStage)`；四个 TargetStage 使用 canonical 值 `discount_50 / discount_20 / withdraw / expired`。
- 相同查询、scheduler 重入或重复物化不得重复该节点。
- 同一 Batch 的不同阶段是不同节点；是否进入当天候选只由各自日期窗口判断。
- 不把 ProductCode、ExpiryDate 或显示文案作为数据库身份替代 BatchId。

### 7.2 同一商品多批次

- 预提醒计算保留批次级节点，便于正确日期与测试对账。
- 集中通知按 ProductId 聚合商品数；同一商品同一预提醒类型的多个批次只计 1 个商品，同时保留批次数用于摘要/测试。
- 同一商品若因不同批次同时命中不同预提醒类型，可分别计入对应类型摘要；整条通知的“涉及商品总数”仍按 ProductId 去重一次。
- 不创建 ProductTask 来完成这种聚合。

### 7.3 正式 Task 与预提醒同日存在

- 只显示一次现有 Windows 集中提醒，不新增第二套通知、scheduler、托盘或后台进程。
- 正式 Task 候选继续按现有 ProductTask HighestStage 权威统计；预提醒不得混入正式 HighestStage 或伪装成待排查任务。
- 通知内容必须明确拆分：`今日待排查` 与 `提前 3 天预提醒`。预提醒按“即将5折 / 即将2折 / 即将收仓 / 即将过期”给出商品数；总涉及商品数按两类候选的 ProductId 并集去重。
- 只有正式 Task 时保持现有信息含义；只有预提醒时不得显示“当前有 N 个商品待排查”或引导用户把它当成可提交的 ProductTask。
- 通知仍只引导正式 Task 进入“待排查任务”页；预提醒没有可处理 Task，不新增页面、按钮或伪入口。
