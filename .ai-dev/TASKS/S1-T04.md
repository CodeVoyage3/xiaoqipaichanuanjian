只建立正式排查主记录、批次明细和明细修改历史的 SQLite/EF Core 数据底座，使一次商品任务的正式提交可永久保存当时快照，并为后续“可修改、不可删除、完整留痕”提供关系约束。本卡不实现提交、修改或跟踪状态重算业务。

## 必须实现

### 1. `inspections`｜一次商品任务的正式记录

至少包含：

- `id`、`task_id`、`product_id`。
- `product_code_snapshot`、可空的 `product_name_snapshot`、可空的 `barcode_snapshot`。
- `stage_snapshot`、`stock_qty_snapshot`。
- `inspector_name`、`check_date`、`submitted_at_utc`。
- 明细集合导航。

约束：

- `task_id` 唯一：一个任务最多生成一条正式排查记录。
- 使用现有 `tasks(id, product_id)` 复合候选键建立外键，数据库拒绝任务与商品错配。
- 商品编码和排查人必填、Trim 后非空；库存快照为非负整数。
- 阶段只允许 `discount_50 / discount_20 / withdraw / expired`。
- 对任务和商品均使用 `NoAction/Restrict`，不得级联删除历史。
- `product_id` 用于关系完整性与查询；历史展示以快照字段为准。

### 2. `inspection_items`｜正式批次明细

至少包含：

- `id`、`inspection_id`、`product_id`、`batch_id`。
- 可空的 `production_date_snapshot`、`expiry_date_snapshot`。
- `stage_snapshot`、`arrival_qty_snapshot`、`checked_qty`、`updated_at_utc`。
- 修改历史集合导航。

约束：

- `UNIQUE(inspection_id, batch_id)`：同次正式排查每个批次最多一项。
- 通过 `inspections(id, product_id)` 与现有 `batches(id, product_id)` 两组复合关系，数据库拒绝跨商品批次。
- 累计到货快照和排查件数均为非负整数；正式记录不允许 `checked_qty = NULL`。
- 阶段值域与正式主记录一致。
- 所有关联均不得级联删除。
- 本卡不新增冗余 `task_item_id` 或候选键；后续提交用例负责从当前任务项生成整组正式明细，避免为尚不存在的服务预建重复关系。

### 3. `inspection_item_revisions`｜明细修改留痕

至少包含：

- `id`、`inspection_item_id`。
- `previous_checked_qty`、`new_checked_qty`、`changed_at_utc`。

约束：

- 修改前后值均为非负整数，且两者不得相等。
- 建立 `(inspection_item_id, changed_at_utc, id)` 查询索引，保证单明细历史可稳定排序。
- 对正式明细使用 `NoAction/Restrict`，不得级联删除修改历史。
- V1 不要求修改原因，不擅自增加原因、修改人或软删除字段。

### 4. 映射、迁移与架构边界

- 延续一实体一 `IEntityTypeConfiguration<T>`，不得把具体映射放回 `StoreDbContext`。
- 只生成一条增量 migration；升级必须保留当前 6 张业务表及其中数据。
- 不改变已有表、索引、约束或 migration 名称。
- 正式记录实体只承载数据；提交完整性、未来日期校验、超库存警告、最新记录判定及跟踪状态重算仍属于后续 Domain/Application 用例。
