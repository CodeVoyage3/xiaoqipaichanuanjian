## 2. 唯一目标与流程

实现 Application 层闭环：

`读取 I01 inspection_plan_v1 Excel → 严格解析数量/身份/快照 → 第一次数据库重读 → 零写入预览 → 用户确认 → 同一事务内第二次重读 → 复用 InspectionDraftUseCase.SaveDraft 原子 patch 既有 Draft`。

## 4. Reader 与文件级契约

Reader 输入为现有绝对 `.xlsx` 文件路径，只读打开 `今日排查计划` 工作表：

- 必须存在 I01 固定 A～Y 25 个表头且顺序/文字完全一致；M～Y 的系统列缺失、重命名或错位均文件级拒绝。
- 每个数据行的 `格式版本` 必须为 `inspection_plan_v1`；空文件、旧版本、混合版本或非本项目格式文件级拒绝并提示重新导出。
- 系统身份/快照列必须使用 I01 类型契约且完整；Task/TaskItem/Product/Batch ID 为正整数文本，AttentionVersion/TaskItem总数/数量快照为非负整数，Task UTC 为可严格解析的 UTC round-trip 值。
- 系统列中的公式、公式错误、缺值或类型漂移均不得使用缓存值猜测，作为对应行错误；`本次排查数量` 含任何公式也一律行级错误，不使用缓存结果。
- A～L 显示列不用于身份纠错；允许整行排序、删除和部分填写。Z 及以后不参与 I02 业务解析。
- Reader 不访问数据库、不写文件、不写任何业务表；文件占用、损坏、路径/权限/Open XML 异常明确返回或抛出失败，不伪装为业务成功。

## 5. 数量和行边界

`本次排查数量` 固定语义：

- 空白单元格 = `null`，表示未完成；若该行被确认应用，则 patch 为 null，可清除该 TaskItem 既有 Draft 数量。
- 数值 `0` = 正式 0；正整数保持原值。
- 非数字、小数、负数、科学计数造成非整数、超过 Int32、公式/公式错误均为行级错误，不得应用。
- 文件中完全缺失的 TaskItem 行不生成 patch，不修改既有 DraftItem，也不视为 0 或完成。
- 同一文件内 TaskItemId 或 BatchId 重复时，涉及的全部重复行均标错；禁止最后一行覆盖。
- 行顺序不影响身份匹配或预览顺序；预览按 `ProductCode(Ordinal) → TaskId → BatchId → TaskItemId` 确定性排序。

## 6. 预览 DTO 与目标选择

预检返回当前会话 DTO，至少包含：

- 文件/格式状态，商品数、Task 数、批次数、填写数、空白数、错误数；
- 每行 TaskId/TaskItemId/ProductId/BatchId、显示商品/批次信息、解析数量、行错误；
- 每个 Task 的可应用/陈旧/失效状态和明确原因；
- `ApplicableTaskIds` 及用于第二次校验的原始 I01 身份/快照，不只返回成功/失败。

预检允许同时展示可应用和不可应用 Task，但零数据库写入。确认请求必须显式提供预览对象及一个或多个唯一正数 TaskId：

- 只能选择该预览中的 `ApplicableTaskIds`；空集合、重复、未知或不可应用 Task 整次拒绝，禁止静默排除。
- 同一 Task 任一在文件中的行有解析/身份/陈旧错误，则该 Task 整体不可应用。
- Task 的行可以只填写一部分或全部空白；只要身份/快照合法，它仍可选择应用，空白按 null patch。
- 同一 Product 的 open Task 仍遵循当前数据唯一性；不因显示字段相同合并 Task。

## 7. 第一次与第二次当前事实校验

预检和最终确认事务内必须调用同一份当前事实校验权威，数据库是唯一当前事实。每个目标 Task 至少验证：

- Task 存在、open、ProductId 一致，且不存在该 Task 的正式 Inspection；
- Product 存在、有效库存大于 0、未库存归零、Managed、批准 policy/version 1，并有匹配完成 ScopeBaseline；
- 当前 TaskItem 集合数量等于导出快照；文件保留行的 TaskItemId/ProductId/BatchId 关系一致，不能绑定新对象；
- 每行 AttentionVersion、Stage、Batch tracking status、CurrentArrivalQty、MaxArrivalQty、Product EffectiveStockQty 与导出快照完全一致；Batch 必须 active；
- Task `UpdatedAtUtc` 与导出 UTC 快照按 SQLite UTC 语义精确一致；同一 Task 各行的 Task UTC、TaskItem总数、Product/库存快照必须内部一致；
- 当前 Draft 不存在 `IsInvalid`；当前任何目标 TaskItem 不得 `RequiresReconfirmation`；
- Excluded、Unresolved、非法 policy/基线、completed、stopped、正式 0 件停止或其他生命周期异常均不可应用。

一个 Task 任一事实冲突，则该 Task 整体不可应用。不得静默绑定新版本、自动 Reconfirm 或用旧 Excel 覆盖新事实。

最终确认必须在同一个外层数据库事务开始后重新读取全部目标；第二次任一冲突时整次确认零写入，并返回/抛出明确冲突。禁止使用预检时已跟踪实体代替复读。

## 8. 排查人、日期与 Draft patch

确认请求必须提供：

- `InspectorName`：Trim 后非空，长度继续受现有 Draft 200 字符门禁；传给每个目标 Task 的值使用规范化结果。
- `CheckDate`：必填，且不得晚于显式 `BusinessDate`。
- `BusinessDate`：显式传入；核心逻辑/测试不读系统墙钟。
- `SavedAtUtc`：显式有效 UTC，供既有 Draft 更新时间语义使用。

对每个目标 Task，按该 Task 在文件中出现的行构造 `SaveDraftRequest` 并调用既有 `InspectionDraftUseCase.SaveDraft`：

- 行内 null/0/正整数原样传入；缺失行不传入、不修改。
- 使用当前再次验证过且等于快照的 AttentionVersion。
- InspectorName/CheckDate 应用于目标 Task 的现有/新 Draft。
- no-change 复用现有 `SaveDraft` 幂等结果；重复应用相同预览且当前事实未变应为 no-change。
- 不调用 `ReconfirmItem`，不修改 RequiresReconfirmation 权威。

多 Task 由一个外层事务包住：全部先复检，通过后逐 Task 调用 `SaveDraft`；任何冲突或保存异常整批回滚并清理 ChangeTracker，不允许部分 Task 留存。返回每 Task DraftId/Changed/Readiness 及整体 Changed。
