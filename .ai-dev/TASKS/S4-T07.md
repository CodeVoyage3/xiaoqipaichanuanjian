## 一、目标与完整边界

把以下已验收 Application 能力接入真实 WPF 排查详情工作区：

- S4-T01 `InspectionTaskQuery.GetDetail`
- S4-T02 `InspectionDraftUseCase.SaveDraft / ReconfirmItem / ClearDraft`
- S4-T03 `ManualInventoryAdjustmentUseCase.Execute`

形成真实链路：

`Dashboard / 待排查列表 → 去排查 → 商品详情 → 检查人/检查日期/批次数量 → 自动保存 → 必要重新确认 → 修正库存 → 返回原来源页面`

本卡不调用 `InspectionSubmissionUseCase`，不实现完成排查、超库存确认、Inspection 创建、HandledAttentionVersion 更新、S3-T06 批次 0 停止或 Task completed。CheckedQty=0 在本卡只保存 Draft。

## 二、详情入口、查询与页面状态

- 待排查列表必须有明确“去排查”入口并携带真实 `TaskId`，不得由 ProductId 猜 Task。
- Dashboard 紧急任务优先直接进入详情；若现有接线代价明显更高，可导航到保留该任务事实的任务列表，但不得提供死按钮。
- 详情唯一读取入口为 `InspectionTaskQuery.GetDetail`。ViewModel/code-behind 不得查询 EF、拼实体图、重新计算 Stage 或复制任务状态规则。
- 必须区分：
  - `open`：完整可编辑详情。
  - `completed`：显示“该任务已完成排查”，只读。
  - `system_closed`：显示“该任务已由系统结束”，只按 DTO 的关闭事实展示。
  - `not_found`：显示“任务不存在或已无法访问”。
- 真正 query 异常显示“排查详情加载失败”与 Retry，写入既有日志；不得伪装成上述业务状态。
- Save/Reconfirm/Adjust 失败后重新 `GetDetail` 判定当前事实；禁止解析异常字符串推导业务状态或创造第五种 Task 状态。

## 三、open 详情内容

商品头至少展示商品名称、编码、条码、最高阶段、有效库存、待排查批次数和次级“修正库存”入口。

待排查批次至少展示：

- 生产日期（null 显示 `—`）
- 有效日期
- Batch 自身实际 Stage，禁止统一替换为商品 HighestStage
- 当前累计到货数量
- 上次正式排查数量与时间
- 本次 CheckedQty
- RequiresReconfirmation 状态与操作

正常活动批次默认折叠为“其他正常批次（X）”，展开后只读展示生产日期、有效日期、当前 Stage、累计到货数量；不得提供编辑或压缩核心录入区域。

## 四、检查信息、CheckedQty 与键盘

- 检查人可恢复、输入和修改；不建设账号、人员表或员工系统。
- 检查日期可恢复；无 Draft 时 UI 默认当天，但合法性只认 S4-T02，UI 不复制未来日期业务规则。
- CheckedQty 明确区分：空白=未检查，0=已检查且现场无该批次，正数=已检查数量。
- 禁止空白/失焦/非法文本静默转 0，禁止负数进入 Application。UI 只做最小可解析非负整数约束。
- Tab 顺序、焦点边框和连续数量录入必须可用；表头在长列表中保持可识别。不得为键盘交互建立新框架。

## 五、Draft 恢复与保存请求

- 进入 open 详情后只恢复 `GetDetail` 返回的有效 Draft：InspectorName、CheckDate、每项 CheckedQty 和 RequiresReconfirmation。
- 不自动创建不存在的 Draft，不把 null 补 0，不自动 Reconfirm。
- `SaveDraftRequest.Items` 只包含 dirty TaskItem patch；每项携带 TaskItemId、BatchId、页面观察的 AttentionVersion 与 CheckedQty。
- 每次保存必须同时携带同一最新 UI 快照中的完整 InspectorName、CheckDate、TaskId、ProductId、BusinessDate、SavedAtUtc。
- 保存结果只用于确认该快照是否持久化；不得用旧 request/result 回写或覆盖更新后的 UI 输入。

## 六、P0：单 Task 串行自动保存

自动保存必须为单 Task 串行队列：

`编辑 → dirty → 短 debounce → 保存一致快照 → 若保存期间再次 dirty，保存完成后继续保存最新快照`

必须保证：

- 任意时刻同一 Task 最多一个 `SaveDraft` 在执行。
- Save A 尚未结束时不会并发启动 Save B。
- 迟到的 A 结果不得把已编辑为新值的 UI、顶部字段或保存状态回退。
- 旧数量保存不得携带旧 InspectorName/CheckDate 在晚写时清空或覆盖新顶部值。
- 页面离开与未来正式提交可以等待队列达到“无 saving、无 dirty”的稳定点。
- 不建立通用调度、消息总线或全局队列框架。

## 七、保存状态、Retry 与离开页面

- 安静显示：未保存、正在保存…、已保存、保存失败；成功不弹 toast。
- 保存失败保留当前 UI 和 dirty，不假装成功、不回滚到数据库旧值，并显示 Retry。
- Retry 必须从当前最新 UI 构建新请求，禁止盲目重放陈旧 request。
- 返回来源页面前：等待正在执行的保存；如仍 dirty，保存最新快照；成功后返回。
- 保存失败时不得静默离开。至少允许 Retry 和留在当前页；如实现明确“放弃未保存修改”，必须有显式确认。

## 八、重新确认与清空草稿

- RequiresReconfirmation 行保留原 CheckedQty，并显示“效期阶段或到货情况已更新，请重新确认”。普通编辑不得本地清除该状态。
- Reconfirm 只调用 `InspectionDraftUseCase.ReconfirmItem`，携带当前 TaskId、ProductId、TaskItemId、BatchId 和页面 AttentionVersion。
- Reconfirm 成功后重新 GetDetail；失败显示稳定错误并重新 GetDetail。UI 不得直接设 false 冒充成功。
- ClearDraft 是低权重动作，必须先确认；只调用 `InspectionDraftUseCase.ClearDraft`。
- ClearDraft 成功后重新 GetDetail；失败不得清除本地输入，不得删除系统失效 Draft 或正式历史。

## 九、库存修正

- 商品头显示当前有效库存和“修正库存”次级入口；用户输入新库存，UI 解析后只调用 `ManualInventoryAdjustmentUseCase.Execute`。
- 正库存成功后重新 GetDetail；`Changed=false / NoChange` 只显示轻量反馈，不伪造 Adjustment。
- 修正为 0 必须先显示危险二次确认：“库存修正为0后，将结束该商品所有批次的效期跟踪。”取消为默认焦点，危险确认不得为默认焦点。
- 用户确认后才传 `ConfirmProductTermination=true`。
- 0 库存成功后：GetDetail 必须真实返回 system_closed，页面切换为不可编辑，并刷新 Dashboard 与 PendingTasks；不得本地猜关闭状态。

## 十、导航与刷新

- 从 PendingTasks 进入详情后，返回必须保留 SearchText、StageFilter、PageNumber；精确像素滚动位置优先，若会显著扩大实现可回原页顶部并在验收记录披露。
- 从 Dashboard 进入详情时保留最小来源事实，返回 Dashboard；不得建设通用导航框架。
- SaveDraft 不刷新 Dashboard/PendingTasks；Reconfirm/ClearDraft/正库存修正刷新 GetDetail；0 库存刷新 GetDetail、Dashboard 和 PendingTasks。

## 十一、异步与 DbContext

- 所有 Application 调用离开明显 UI 阻塞路径。
- 每次后台操作独立创建、使用并释放 `StoreDbContext`。
- 禁止多线程共享或长期持有 DbContext；ViewModel 不得持有 tracked entity、DbSet、IQueryable。
- UI 只持有普通 DTO/result；不得新增 DI、Repository、UnitOfWork、EventBus 或通用导航/MVVM框架。
