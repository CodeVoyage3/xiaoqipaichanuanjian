## 目标

实现一个独立、可复用的 Application 后置用例，只消费 Stage 2 成功导入已经明确产生并冻结的商品/批次事实，完成：

- 真正新批次开始跟踪；
- 活动 Batch 的累计到货首次突破导入前历史最高时，递增现有关注版本并重新关注当前效期阶段；
- 仅因正式排查 0 件停止的旧 Batch，在全部例外条件成立时恢复跟踪并记录批准事件。

本卡不解析 Excel，不从提交后的数据库状态反推“新批次”或“真正新增到货”，不接入真实导入运行链路。S3-T07 再负责在成功导入后构造冻结请求并调用本用例。

## 已核验事实与唯一口径

- Stage 2 `ImportPlan.NewBatches` 已明确“数据库历史唯一键从未出现”的新批次；有生产日期时唯一键为 `商品编码 + 生产日期 + 有效日期`，无生产日期时为 `商品编码 + 有效日期`。
- `BatchUpdatePlan.FieldChanges` 保存明确的 `Before` / `After`；Planner 对 `MaxArrivalQty` 固定写入 `max(导入前 MaxArrivalQty, 本次 CurrentArrivalQty)`。因此真正新增到货必须由冻结输入中的 `CurrentArrivalQty > PreviousMaxArrivalQty` 判断，不得用导入后 `CurrentArrivalQty == MaxArrivalQty` 猜测。
- Product 已有 `EffectiveStockQty`、`LifecycleGeneration`、`IsStockZeroTerminated`、`LastSeenImportId`；Batch 已有 `LifecycleGeneration`、`TrackingStatus`、`StopReason`、`StoppedAtUtc`、`CurrentStage`、`NextTriggerDate`、`AttentionVersion`、`HandledAttentionVersion`、`LastSeenImportId`，无需平行字段。
- S3-T04 canonical generation：商品首次正式归零时 Product generation checked 加一；全部旧 Batch 保留旧 generation 并永久停止；库存恢复不清除 `IsStockZeroTerminated`；归零后的真正新批次使用 Product 当前 generation 开启新周期。
- canonical 跟踪状态使用 `active` / `stopped`；本卡将“正式排查结果 0 件停止”的唯一原因固定为既有批准代码 `batch_checked_zero`。恢复后为 `active`、`StopReason = null`、`StoppedAtUtc = null`。
- 恢复事件只用既有 `batch_tracking_resumed`，`BatchId` 必填且与 Product 匹配，`SourceImportId` 指向本次成功 Import；稳定 Reason 使用 `new_arrival_after_batch_checked_zero`。普通新批次和活动批次新增到货不创建 LifecycleEvent。
- S3-T01 `ExpiryStageCalculator` 是阶段/下一触发日唯一实现；S3-T02 `ProductTaskAggregator` 是开放商品任务唯一实现；S3-T04 是商品归零唯一状态机。
- 自然阶段推进不改变 AttentionVersion；真正新增到货才是本卡批准的新关注事实。`HandledAttentionVersion` 本卡不修改，也不得把它改造成导入幂等标记。

## 最小冻结输入契约

新增一个具体 Application 用例及最小请求/结果类型，不增加接口层级。请求至少包含：

- `ImportId`：已经持久化的来源 Import；必须 `Status == Succeeded`、`IsUndone == false`。
- `BusinessDate`：显式 `DateOnly`，传给 S3-T01；不得读取系统日期。
- `OccurredAtUtc`：显式 UTC，作为状态更新时间和恢复事件时间；不得读取系统当前时间。
- 一个或多个显式 Product 分组；每组包含正整数 `ProductId` 和本次明确出现的 Batch 事实。
- 每个 Batch 事实包含正整数 `BatchId`、明确的事实种类 `new` 或 `existing`、`PreviousMaxArrivalQty`、`CurrentArrivalQty`。
- `existing` 事实还必须冻结 `ExpectedAttentionVersionBefore` 与 `TargetAttentionVersionAfter`；真正新增到货时 target 必须精确等于 `checked(expected + 1)`，未突破历史最高时 target 必须等于 expected。

请求是由成功导入的 Stage 2 before/after/new 事实一次性冻结的不可变业务输入。生产代码不得接收工作簿、解析结果或自行重算 ImportPlan；也不得提供“扫描某个 Import 的全库差集”入口。

执行前一次性验证全部输入，任何一项非法则整次拒绝且无业务副作用：

- Product、Batch、Import 存在；Batch 属于指定 Product；ProductId/BatchId 不重复。
- Product 与 Batch 的 `LastSeenImportId` 均等于请求 ImportId，证明它们是本次明确出现的行；该字段只作正向来源门禁，不得反向查询缺失集合或据此推断 new/arrival。
- 数据库中 Batch 的当前累计到货与历史最高必须等于 Stage 2 已提交的冻结 after 值：`CurrentArrivalQty == 输入 CurrentArrivalQty`，`MaxArrivalQty == max(PreviousMaxArrivalQty, CurrentArrivalQty)`；不一致属于 stale/conflicting request。
- `new` / `existing` 只信任并校验调用方冻结事实，不得通过数据库是否存在来反推；Batch 在成功导入后必然已经存在。
- 数量和版本均非负，版本加一使用 checked arithmetic；非 UTC 时间拒绝。
- Product 当前库存必须大于 0。若直接误调用到当前库存 0 的任一 Product，必须在任何写入前拒绝整个请求；不得在本卡复制或调用第二套归零状态机。

不得为了方便直接让 S3-T05 依赖 `ConfirmedImportExecutor`，也不得修改该执行器。S3-T07 可从已冻结的 Stage 2 合同映射为本 DTO。

## 持久化幂等契约

现有 schema 可由 `Batch.AttentionVersion` 承担真正新增到货的持久化 compare-and-set，无需 migration：

- 首次处理真正新增到货：数据库版本必须等于 `ExpectedAttentionVersionBefore`，用例将其改为 `TargetAttentionVersionAfter = checked(expected + 1)`。
- 完全相同冻结事实重放：数据库版本已经等于 target，视为该批次事实已应用；该 Batch 不再递增版本、不再恢复、不再调用聚合器、不再写事件或污染 Draft。
- 数据库版本既不等于 expected 也不等于 target：拒绝 stale/conflicting request，不猜测、不覆盖。
- 后续不同 Import 的新关注事实必须携带新的 expected/target 对；不得在重试时根据当前数据库重新生成旧请求。

真正新批次不递增 AttentionVersion。重复处理同一 `new` 事实只重复验证并计算相同终态；S3-T02 对相同 Batch/Stage/AttentionVersion 本身幂等，且本场景没有恢复事件，因此不得新增专用处理标记。

若实现时证明上述现有字段 compare-and-set 无法满足真实 SQLite 原子性或精确重放，立即停止并报告 Sol；不得新增字段、表或 migration。

## 处理优先级与状态转换

### 1. 商品归零最高优先级

- 当前 `EffectiveStockQty == 0`：整次预校验拒绝、无任何 S3-T05 状态转换。
- `IsStockZeroTerminated == true` 且事实为旧 `existing` Batch：该历史 Batch 永久不恢复、不递增版本、不生成任务或事件。
- `IsStockZeroTerminated == true`、当前库存大于 0 且事实为真正 `new` Batch：允许进入 Product 当前 generation 的新周期。
- 不修改 Product 的库存、归零标记或 generation，不调用/复制 S3-T04 状态机。

### 2. 真正新批次

对明确 `new` Batch：

- 设置 `LifecycleGeneration = Product.LifecycleGeneration`、`TrackingStatus = active`、`StopReason = null`、`StoppedAtUtc = null`。
- 调用 S3-T01，以显式 BusinessDate 和 Batch 现有有效日期/保质期值/单位直接计算今天的 `CurrentStage` 与 `NextTriggerDate`；不回放历史阶段。
- 当前阶段为 `none` 时只跟踪并保存下一触发日，不创建任务。
- 当前阶段为 `discount_50` / `discount_20` / `withdraw` / `expired` 时交给 S3-T02；不得复制聚合逻辑。
- 不创建第二个 Batch，不修改唯一键、到货量、Product generation 或 AttentionVersion。

### 3. 活动 Batch 的真正新增到货

唯一判断为 `CurrentArrivalQty > PreviousMaxArrivalQty`。`8→5→6→8` 均不触发；`8→10` 才触发。差值不写入任何排查数量。

对 `TrackingStatus == active` 且首次应用的真正新增到货：

- 通过版本 compare-and-set 将 AttentionVersion 加一。
- 调用 S3-T01 直接计算今天的当前阶段和下一触发日并更新 Batch；不回放已完成或离线错过阶段。
- 先在同一外层事务/同一 StoreDbContext `SaveChanges`，再以新 AttentionVersion 调用 S3-T02，使聚合器读取到当前事务可见版本。
- 当前阶段需要排查时加入/升级商品唯一开放任务；明确传入重新确认要求。已有 Draft/DraftItem 内容与 ConfirmedAttentionVersion 保留，由 S3-T02 设置 RequiresReconfirmation。
- 当前阶段为 `none` 时不创建任务，但关注版本仍持久化递增。
- 已完成旧任务不复活；若今天仍是相同阶段，可创建新的当前阶段开放任务；若今天已跨阶段，只创建今天的阶段。

未首次突破历史最高时，不改变阶段、版本、任务、Draft 或事件。

### 4. 已停止旧 Batch 的唯一恢复例外

只有以下条件同时成立才恢复：

1. `TrackingStatus == stopped` 且 `StopReason == batch_checked_zero`；
2. Product `IsStockZeroTerminated == false`；
3. Product 当前 `EffectiveStockQty > 0`；
4. 本次真正新增到货，且版本 compare-and-set 是首次应用。

恢复时：

- `TrackingStatus = active`、`StopReason = null`、`StoppedAtUtc = null`；保留并要求 Batch generation 与 Product 当前 generation 一致，不递增 Product generation。
- AttentionVersion 按上述规则加一，调用 S3-T01 直接得到今天阶段/下一触发日。
- SaveChanges 后调用 S3-T02；`none` 不创建任务，待排查阶段只生成今天的当前任务。
- 写一条 `batch_tracking_resumed`，关联正确 Product、Batch、SourceImportId；不得新增 new-arrival 事件类型。

以下全部无恢复副作用：Product 曾商品级归零、库存仍为 0、停止原因不是 `batch_checked_zero`、只回升到旧最高、只是再次出现在 Excel。尤其 `>0 → 0 → >0` 后的旧 Batch，即使 `8→10` 也永久停止；只有真正新键可以进入新 generation。

## 查询范围与事务

- 只按请求中的 ProductId/BatchId 定向查询；不得全库扫描 Product/Batch，不得查询本次未出现对象，不得用 `LastSeenImportId` 做反向差集。
- 一个请求内 Product、Batch、AttentionVersion、Tracking 状态、ProductTask、TaskBatchItem、Draft、LifecycleEvent 使用同一 StoreDbContext 和明确数据库事务。
- 无当前事务时用例拥有事务并统一提交/回滚；存在外层事务时加入，不嵌套提交，由调用方最终 commit/rollback。
- 先完成全请求验证，再变更；所有 Batch 变更先 SaveChanges，使 S3-T02 看见新版本，然后按 Product 分组每个商品调用聚合器一次，最后统一提交。
- 中途失败时不得留下 Batch/版本/Task/Item/Draft/Event 半状态；自有事务回滚后清理 ChangeTracker，外层事务异常时不得擅自提交。
- 不在生产代码添加测试故障开关；用真实 SQLite trigger/约束注入失败。
