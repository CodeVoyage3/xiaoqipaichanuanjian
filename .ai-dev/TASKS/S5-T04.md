# S5-T04｜正式排查历史修改 UI

## 目标

在 S5-T02 已完成正式排查记录修订与 Revision 留痕、S5-T03 已完成历史只读 UI 的基础上，为正式排查历史详情增加受控的数量修订入口。

本任务只做“历史数量修改 UI”：

- 从历史详情发起修改；
- 调用既有 `InspectionHistoryEditUseCase`；
- 修改成功后刷新当前正式值与 Revision 历史；
- 明确展示成功 / 无变化 / 失败状态；
- 保持 Stage 3 / Stage 4 权威行为完全不变。

本任务不进行全局 UI 重设计。视觉仅要求与当前 Stage 4 / Stage 5 页面一致、功能清楚、基本可用。统一 UI/UX 重构留到 Stage 7 之后。

## 核心范围

### 1. 历史明细修改入口

仅对允许修订的正式 `InspectionItem.CheckedQty` 提供编辑入口。

要求：

- 必须从明确选中的正式历史明细发起；
- 只允许修改数量；
- 不允许修改商品身份、批次身份、快照、库存、阶段、提交时间等其他字段；
- 不允许修改非 completed 正式记录；
- 不允许从 Draft 或待排查页面调用该历史修改入口。

### 2. 修改交互

修改流程至少包含：

1. 进入编辑状态；
2. 输入新的排查数量；
3. 基本输入校验；
4. 用户明确确认提交；
5. 调用 `InspectionHistoryEditUseCase.Execute`；
6. 根据后端结果反馈；
7. 成功后刷新当前值和 Revision 历史。

不得在 UI 中自行复制业务校验逻辑替代后端用例。

### 3. 后端结果映射

UI 必须正确处理既有结果：

- `changed`
  - 明确提示修改成功；
  - 刷新当前正式数量；
  - 刷新 Revision 历史；
  - 新 Revision 可立即看到。

- `no_change`
  - 不显示为错误；
  - 明确提示“数量未变化”或等价文案；
  - 不制造虚假 Revision。

- `not_found`
  - 明确提示记录不存在 / 已失效；
  - 刷新当前详情或返回安全状态；
  - 不崩溃，不保留误导性的编辑成功状态。

- validation / transaction / persistence failure
  - 明确失败提示；
  - 不更新界面为新值；
  - 不伪造 Revision。

### 4. 编辑期间状态控制

要求：

- 提交过程中禁止重复提交；
- 修改完成前避免用户切换目标造成错误写入；
- 失败后允许用户继续查看原历史数据；
- 重新加载后必须以数据库正式结果为准；
- 关闭编辑状态不得修改任何业务数据。

### 5. Revision 联动

修改成功后：

- 当前数量显示最新值；
- Revision 区域立即刷新；
- 顺序继续使用后端返回顺序；
- UI 不自行计算 Revision 链；
- 不制造“初始 Revision”。

## UI / 视觉原则

本任务不解决整体视觉不满意问题。

只要求：

- 与现有 Stage 4 / S5-T03 风格一致；

## GUI 验收

本任务涉及真实 WPF UI，最终 GUI 由用户本人验收。

Sol 不使用电脑操控做 GUI 验收。

技术验收完成后，仅向用户提供精简清单，建议至少验证：

1. 能从历史详情选中一条明细进入修改；
2. 修改数量并确认后，当前值正确更新；
3. Revision 区域出现对应“前值 → 后值 → 时间”；
4. 同值修改不会新增 Revision；
5. 非法数量 / 失败场景不会假装成功；
6. 页面没有回滚、删除、撤销等越界功能；
7. 1024×600 / 125% 下修改操作可完成。

视觉观感不作为本任务返工门槛，除非已经影响可读性或操作。
