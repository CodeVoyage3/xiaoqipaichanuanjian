## 二、完成排查入口与保存 P0 门禁

- open 详情显示高权重“完成排查”主按钮；completed/system_closed/not_found/Error 不得显示可执行提交。
- 提交前必须占用单次提交门禁，并等待 S4-T07 单 Task 保存队列稳定：无 saving、无 dirty、最近保存成功。
- 等待期间再次 dirty 时继续保存最新一致快照；禁止数据库旧 Draft 被提交。
- 保存失败或 dirty 无法落库时禁止调用 Submission，显示“草稿尚未保存成功，请先重试保存。”，保留 Retry 和本地输入。
- 页面 readiness 只做轻量提示，不得替代 Application 数据库重读与授权。
- 提交请求只传 TaskId、ProductId、BusinessDate、SubmittedAtUtc，以及用户明确确认时由 Application 返回的库存/合计绑定事实。

## 三、提交互斥与状态

- 点击后显示“正在提交…”，重复点击只能进入一次 Submission。
- 提交期间禁止再次提交、ClearDraft、Reconfirm、库存修正、检查人/日期/数量编辑和状态不明的导航离开；不得仅依赖 disabled 防重。
- 所有 Application 操作继续采用独立后台 DbContext 生命周期；ViewModel 不得持有 DbContext、DbSet、IQueryable 或 tracked entity。

## 四、Submitted 与 AlreadySubmitted

- `Submitted`：显示“排查已完成”，重新 GetDetail，真实映射 completed；刷新 Dashboard/PendingTasks，开放列表移除任务；退出 Draft 保存/编辑/Reconfirm/ClearDraft/库存修正/提交状态。
- `AlreadySubmitted`：作为合法幂等结果映射 completed 并刷新三处，不重复正式动作或清理。
- Task completed 但无 Inspection 等数据不一致不得冒充 AlreadySubmitted；显示“任务状态异常，无法完成排查。”并记录详细异常，不得自行修复。
- 成功提交与随后刷新失败必须隔离：保持“排查已完成”，另报首页或任务列表刷新失败，不得诱导重复提交。

## 五、超库存确认

首次 `RequiresOverStockConfirmation` 必须显示当前有效库存、排查合计和超出量，并提供：

1. 返回修改排查件数；
2. 进入现有库存修正；
3. 确认仍然提交。

确认事实只绑定本次 Application 返回的 `EffectiveStockQty + TotalCheckedQty`。再次 Submit 传 `ConfirmedEffectiveStockQty` 与 `ConfirmedTotalCheckedQty`。任何返回编辑、Draft 变化、库存修正、Task/库存/合计变化都立即废弃旧确认；后续必须重新等待保存并由 Application 再判定，禁止永久 `ConfirmOverStock=true`。

## 六、陈旧、并发关闭、NotFound 与异常

- 提交时 AttentionVersion/RequiresReconfirmation 变化：显示稳定提示，重新 GetDetail，open 页面显示真实 Reconfirm；不创建 stale 第五状态。
- Task 被并发 system_closed：重新 GetDetail 后映射终止态并刷新 Dashboard/PendingTasks。
- not_found：显示“任务不存在或已无法访问”并提供返回列表，不允许无限重试提交。
- 真正数据库/IO异常：显示“排查提交失败，请重试。”并记录详细异常；重新 GetDetail 恢复事务回滚后 Draft。若刷新也失败，保留当前可见输入与刷新错误。
- CheckedQty=0 在提交成功前仍只是 Draft；只有 S4-T04 成功后才能体现 S3-T06 的 stopped/batch_checked_zero 事实。
