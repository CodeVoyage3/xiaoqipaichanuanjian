# S5-T02｜正式排查记录修改留痕 / Revision 基础

## 目标

在 S5-T01 已建立“正式排查历史只读查询”的基础上，为正式排查记录建立可追溯修改能力：

- 正式记录允许按既定规则进行修改；
- 修改不能覆盖掉原始历史事实；
- 每次修改必须形成 Revision / 修改留痕；
- 修改后的当前值与历史版本都可被稳定读取。

本任务只建立后端 / 应用层基础，不做 WPF 历史页面。

## 实施前必须先核对仓库事实

Luna 开始前必须读取并确认：

1. `.ai-dev/STAGES/STAGE-5-HANDOFF.md`
2. `.ai-dev/ACCEPTANCE/S5-T01.md`
3. `S5-T01` 实现与测试
4. `Inspection` / `InspectionItem` 的实际实体、字段、关系和 EF 配置
5. Stage 1～4 中是否已经存在 Revision、历史版本、修改记录或类似基础设施
6. 当前 `master` / HEAD / `git status`
7. 当前 migration 数量与 schema

禁止仅凭任务卡假设已有 Revision 表、字段或修改机制。

如果仓库事实已存在可复用的修改留痕结构，优先复用，不新建平行体系。

## 核心范围

### 1. 正式记录修改用例

为已正式提交、可识别的 Inspection 提供修改入口。

修改对象以仓库现有正式排查数据模型为准，至少围绕正式排查明细中的可修正结果字段。

必须满足：

- 只能修改已经正式存在的 Inspection / InspectionItem；
- 不允许把 Draft 直接当成历史修改；
- 不允许重新走 Stage 4 Submission；
- 不允许通过修改历史触发生命周期重算；
- 不允许修改 ProductTask 完成状态；
- 不允许把历史修改解释成一次新的正式排查。

具体可修改字段必须以当前业务模型和既有数据事实为准，不得自行扩大到商品主数据、批次身份、库存、效期阶段等无关领域。

### 2. Revision 留痕

每一次成功修改都必须产生可追溯记录。

Revision 至少需要能够回答：

- 修改的是哪一条正式排查记录；
- 修改的是哪一条正式排查明细；
- 修改发生时间；
- 修改前的值；
- 修改后的值。

如果仓库已有更完整的 Revision 设计（例如 RevisionId、Reason、字段级快照、版本号等），以仓库既有设计为准。

禁止：

- 直接覆盖旧值而不留痕；
- 修改后删除旧版本；
- 通过日志文本代替结构化 Revision 数据；
- 为了方便 UI 展示而制造不可追溯的冗余副本。

### 3. 原子性

一次历史修改必须是事务性的。

要求：

- 当前正式值更新与 Revision 写入必须在同一事务中成功；
- Revision 写入失败时，正式值不得被部分修改；
- 正式值修改失败时，不得留下孤立 Revision。

### 4. 只读查询衔接

S5-T01 的历史查询行为必须继续成立。

如本任务需要扩展查询能力，应只做最小必要扩展，使后续能够读取：

- 当前正式值；
- 对应 Revision 历史。

不得因此重写 S5-T01 的列表/详情语义。

## Schema / Migration 门禁

S5-T02 是否需要 schema 变化，必须先由仓库事实决定。

### 若现有 schema 已具备 Revision 基础

- 必须复用；
- migration 保持 8；
- 不允许为了“结构更漂亮”新增表或字段。

### 若现有 schema 确实无法实现结构化 Revision

Luna 不得自行新增 migration 后继续实施。

必须先：

1. 明确说明现有 schema 缺口；
2. 给出最小 schema 方案；
3. 停止；
4. 由 Sol 单独审查并决定是否批准 migration。

未经 Sol 明确批准，不得将 migration 从 8 增加到 9。

## 最低测试要求

至少覆盖：

1. 已正式完成的 InspectionItem 可以按允许字段修改
2. 每次修改都会产生 Revision
3. Revision 正确保存修改前值
4. Revision 正确保存修改后值
5. 连续两次修改形成两条有序历史
6. 修改不存在的 Inspection / Item 返回既定 not-found 语义
7. Draft / 未正式记录不能通过本用例修改
8. Revision 写入失败时正式值不变化
9. 正式值更新失败时不产生孤立 Revision
10. 修改历史不改变 ProductTask 完成状态
11. 修改历史不触发 Stage 3 Lifecycle
12. S5-T01 历史查询继续通过
13. Stage 4 Submission / Draft / Reconfirm / InventoryAdjustment 权威测试继续通过
14. Stage 3 生命周期权威测试继续通过

测试目录、命名与 fixture 必须沿用仓库现状，不创建平行测试体系。

## 完成定义

只有当：

- 正式排查记录修改能力成立；
- 每次修改均具备结构化 Revision 留痕；
- 修改与 Revision 原子一致；
- S5-T01 查询与 Stage 3 / Stage 4 权威行为无回归；
- schema / migration 完全符合门禁；
- 全部技术验收通过；

才可将 S5-T02 判定为完成。

完成后停止。

不得创建、编号、派发或实施 S5-T03，等待下一步批准。
