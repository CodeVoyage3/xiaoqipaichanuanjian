## 2. 唯一目标

实现一个薄 Application orchestrator：

`明确的多 Task 请求 → 全量只读边界预检 → 单一外层事务 → 按 TaskId 稳定顺序复用 InspectionSubmissionUseCase.Submit → 全部成功或全部回滚`。

正式结果必须与用户在现有详情页逐 Task 调用同一 `Submit` 一致。本卡不做 WPF。

## 3. 最小实现与禁止复制

## 4. 请求与结果契约

建议最小请求：

`BulkInspectionSubmissionRequest(TaskIds, InspectorName, CheckDate, BusinessDate, SubmittedAtUtc, OverStockConfirmations)`

冻结规则：

- TaskIds 必须为非空、唯一正数集合；重复、空或非正数整次拒绝。处理顺序固定为 TaskId 升序，输入顺序不影响业务结果。
- InspectorName Trim 后必填且不超过 200；CheckDate/BusinessDate 不得为 default，CheckDate 不得晚于 BusinessDate；SubmittedAtUtc 必须为 UTC。
- InspectorName/CheckDate 是本批用户确认的 Draft 身份，必须与每个目标当前有效 Draft 的规范化值完全一致；I03 不修改 Draft。
- 超库存确认项为唯一正数 TaskId + 非负 `EffectiveStockQty / TotalCheckedQty`；不得含目标外、重复或部分字段。无确认时使用空集合。

结果至少包含整体状态、按 TaskId 排序的单 Task 结果/InspectionId，以及当前全部超库存确认事实：TaskId、ProductId、EffectiveStockQty、TotalCheckedQty。

批量整体状态冻结为：

- `Submitted`：本次所有目标刚刚在同一事务成功提交。
- `AlreadySubmitted`：所有目标均已由完全相同请求提交，零新增写入。
- `RequiresOverStockConfirmation`：当前存在超库存 Task，尚未提供确认；整批零写入并返回全部当前值。
- `OverStockConfirmationStale`：已提供确认集合/数值与当前全部超库存事实不完全一致；整批零写入并返回全部当前值（当前列表可为空）。

open/completed 混合、completed 但请求签名不一致、非法/陈旧 Task 等不伪装为幂等，明确冲突异常并整批零写入。

## 5. 全量预检

在调用任何 Submit 前，在外层事务中按当前数据库一次性重读全部目标并逐 Task 验证：

- Task 存在且状态为 open，或全部为可证明同请求的 completed；不支持 system_closed/未知状态。
- Product、TaskItem、Batch 关系一致；Task 至少一个当前 TaskItem。
- Product 为 Managed、批准 policy/version 1、EffectiveStockQty 非负、未库存归零，并有匹配完成 ScopeBaseline；Excluded/Unresolved/非法 policy 零进入。
- Draft 存在且有效，InspectorName/CheckDate 与请求相同；DraftItem 精确覆盖当前 TaskItem，数量均已填写且非负。
- 不存在 RequiresReconfirmation；DraftItem ConfirmedAttentionVersion 与 TaskItem/Batch 当前 AttentionVersion 一致。
- Batch 必须 active，current stage 与 TaskItem stage 一致，当前/最大到货非负，HandledAttentionVersion 合法且不大于 AttentionVersion。
- open Task 不得已有正式 Inspection。

该层只补现有单 Task Submit 未覆盖的跨 Task/lifecycle 防御，不创建正式实体。任一目标预检失败，整批拒绝，不调用 Submit，不处理其余“合法部分”。

completed 幂等只允许所有 Task 均 completed 且各自存在唯一 Inspection，并与本请求的 Task/Product、规范化 InspectorName、CheckDate、SubmittedAtUtc 完全一致；InspectionItem 必须覆盖原目标事实。任一不一致或 open/completed 混合均为冲突。

## 6. 单事务与集中超库存流程

在一个可靠外层事务中：

1. 完成 §5 全量预检。
2. 全部 completed 且同请求：返回 `AlreadySubmitted`，零写入。
3. 对全部 open Task 按 TaskId 升序调用现有 `Submit`，第一次均不传超库存确认；收集所有 `RequiresOverStockConfirmation`，正常 Task 的写入仍仅为未提交事务内变更。
4. 若出现任一 warning：
   - 请求无确认：回滚整批，返回所有当前 warning；
   - 请求确认集合/值与所有当前 warning 不完全相等：回滚整批，返回 `OverStockConfirmationStale` 和所有当前 warning；
   - 完全相等：只对 warning Task 在同一事务内再次调用 `Submit`，传入该 Task 精确当前确认值。
5. 若当前无 warning 但请求携带任何确认：视为旧确认，回滚并返回 `OverStockConfirmationStale`。
6. 最终每个目标必须且只产生 `Submitted`；任何异常、warning、AlreadySubmitted 或保存失败均整批回滚并清理 ChangeTracker。
7. 全部成功后统一 Commit。

该流程允许第一次调用对普通 Task 产生未提交事务内写入，但任何 warning/冲突都会整体 rollback，数据库对外保持零写入；不建设第二套 dry-run 提交逻辑。

## 7. 0 件、正数与历史

- 0 件继续走单 Task Submit 内既有 `BatchCheckedZeroLifecycleUseCase`；orchestrator 不手工改 TrackingStatus。
- 正数继续既有生命周期，仅完成当前 Task；不得永久屏蔽后续更高 Stage。
- 成功后现有 `InspectionHistoryQuery` 必须可见所有 Inspection/InspectionItem。
- 不创建 Revision；不增加 BulkSubmission/BatchSubmission 历史实体。

## 8. 原子性与幂等

- 第 N 个 Submit 异常时，前 N-1 个 Inspection/Item、Task completed、Draft 删除、Batch stopped、LifecycleEvent 和版本推进全部回滚。
- 第一次超库存 warning 时，正常 Task 的未提交结果也全部回滚。
- 完全相同请求对“全部已成功”集合重放返回 `AlreadySubmitted`，不创建第二份 Inspection/LifecycleEvent。
- 部分 completed、部分 open 必须整体冲突；禁止只提交 open 子集。
- 请求目标集合本身就是本次确认边界；不得静默增删 Task。

- 单 Task、多 Task、多商品、单商品多批次与确定性 TaskId 顺序；
- 0 件停止、正数继续、0+正数组合，结果与逐 Task Submit 一致；
- 所有 Inspection/Item 正确、历史查询可见、无 Revision；
- 第二 Task 异常导致第一 Task 的 Inspection/Task/Draft/Batch/Lifecycle/版本完整回滚；
- TaskId/人员/日期/UTC/确认项请求门禁；
- 缺失/invalid/incomplete Draft、RequiresReconfirmation、Attention/Stage/库存/到货/tracking/关系陈旧；
- completed、system_closed、已有 Inspection、Excluded/Unresolved/非法 policy/无基线；
