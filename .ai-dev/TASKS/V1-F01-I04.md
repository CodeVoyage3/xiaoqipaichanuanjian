## 4. Policy-aware 正常生命周期契约

### 4.1 统一资格

只有同时满足以下条件的 Product 才能进入效期计算、Task 与 Reminder 链路：

- `ExpiryManagementStatus == Managed`；
- `PolicyCode` 是 V1 批准值且 `PolicyVersion == 1`；
- 存在 `IsCompleted == true` 且 `ScopeKey == CategoryCode`、PolicyCode、PolicyVersion 全部匹配的 ScopeBaseline；
- 当前库存及 Batch tracking 状态满足既有对应入口条件。

不得仅因存在任意完成 baseline、任意 policy 或历史 BatchBaseline 就放行。I04 不创建、不修改、不重置 ScopeBaseline / BatchBaseline，不调用 I03 重新执行首次冷启动。

### 4.2 Policy 计算

`PostImportLifecycleUseCase` 与 `StartupRecalculationUseCase` 必须使用现有 `ExpiryPolicyCalculator` 的 Product policy identity，而不是食品专用 `ExpiryStageCalculator.Calculate`：

- `food_expiry / 1` 保持现有食品阈值；
- `pet_expiry / 1` 使用批准宠物阈值；
- `general_long_expiry / 1` 只处理已保存为 Managed 的 `>180` 天通用长效商品；
- 到期当天仍为 `expired`，月份仍固定 30 天；
- 非 version 1、未知/不匹配 policy 必须拒绝或排除，不能猜测降级到食品规则。

Policy-aware 计算只在 Application/Domain 权威位置调用一次；导入编排、WPF 和 Reminder 不复制阈值。

### 4.3 Excluded / Unresolved

Excluded（至少 `seasonal_assortment`、`gift_sample`）与 Unresolved：

- Product / Batch 与既有导入提示继续保留；
- 不计算或推进效期 Stage / NextTriggerDate；
- 不创建、升级或恢复 ProductTask；
- 不进入 Reminder 候选；
- 不创建 ScopeBaseline / BatchBaseline，也不被 I03 重跑。

若数据库中存在与上述状态矛盾的异常 open Task，本卡不得静默改写正式历史或把异常事实伪装成正常；应以最小读取门禁确保 Reminder 不消费非 Managed Task，并用测试固定行为。不得新增清理 migration 或隐式数据修复。

## 5. Post-import 生命周期

确认导入继续使用既有 Stage 2 + lifecycle 外层事务：

1. I03 对未完成范围执行首次冷启动；同次新完成 scope 仍不得再跑普通 post-import / stock-zero，避免首次 5折/2折被补成 Task。
2. 已完成 scope 不再执行冷启动，按普通 I04 生命周期处理本次合法 Product/Batch facts。
3. 真正新 BatchKey：直接用匹配 policy 计算当前 Stage，Stage > none 时聚合 Task；none 只设置正确下一触发日。
4. 既有 Batch 只有 `CurrentArrivalQty > PreviousMaxArrivalQty` 即首次突破历史 MaxArrivalQty 时按既有 compare-and-set 增加 AttentionVersion，并在当前 Stage 重新触发/升级 Task；未突破不得误触发。
5. 只允许既有 `batch_checked_zero` 且同生命周期代、商品从未归零、库存为正、真正新增到货的 Batch 恢复；其他 stopped Batch 不恢复。
6. 商品明确库存 0 继续优先于新批次、新到货、恢复和阶段 Task；归零关闭 Task/失效 Draft 的既有权威不变。

PostImportLifecycleUseCase 的直接调用也必须验证 Product 的 Managed、policy/version 与完成 ScopeBaseline，不能只依赖 orchestrator 过滤。

## 6. Startup 正常重算

StartupRecalculationUseCase 必须：

- 只选中符合 §4.1、active 且触发日到期的 Batch；
- 按 Product policy-aware 计算当前最高 Stage，并更新 CurrentStage / NextTriggerDate；
- 复用 ProductTaskAggregator 做商品聚合与最高 Stage；
- 支持 5折 → 2折 → 收仓 → 过期的后续升级，允许离线跨阶段直接计算当前结果，不回放中间历史任务；
- 正式提交后，当 Batch 后续进入更高 Stage 时重新创建/升级 open Task；不得把 HandledAttentionVersion 或既有 Inspection 当成永久屏蔽；
- 相同 BusinessDate / 相同事实重复启动幂等，不重复 ProductTask/TaskItem，不改写已稳定事实；
- 不重新执行 I03，不把 I03 的 discount50/discount20 baseline 追补成“历史漏任务”。只有 BusinessDate 到达后续更高触发点时才进入正常生命周期。

## 7. ProductTask、正式提交与历史权威

- 批次触发、商品聚合；每商品最多一个 open ProductTask。
- HighestStage 继续严格为 `expired > withdraw > discount_20 > discount_50`；禁止字符串排序或第二套计算。
- TaskItem 保持 BatchId、Stage、AttentionVersion 与 RequiresReconfirmation 的既有语义。
- 阶段升级或更高 AttentionVersion 继续由 ProductTaskAggregator 合并；不得重复建商品任务。
- 正式提交继续由现有 Submission 用例创建 Inspection / Item、推进 HandledAttentionVersion、完成 Task 与处理 Draft；I04 不复制、不重写提交事务。
- 正式提交、Inspection 与 Revision 是历史权威；I04 不改写已有历史，不创建补偿历史，不因启动重算重放 Revision 或正式 0 件 LifecycleEvent。

## 8. Reminder 契约

I04 只验证并保持现有 Reminder 对 open ProductTask 的消费：

- 合法 Managed open Task 正常成为 ReminderCandidate，并保持现有到点判断、同日幂等、scheduler、托盘与成功登记语义；
- Excluded、Unresolved、无匹配完成 baseline 或无有效 policy 的商品不进入 Reminder；
- Reminder 不计算 Stage、不创建 Task、不修改 Stage 日期；
- 禁止任何“提前 3 天”预提醒、提前候选、阈值偏移或新通知状态；该能力仅属于未批准的 V1-F02。
