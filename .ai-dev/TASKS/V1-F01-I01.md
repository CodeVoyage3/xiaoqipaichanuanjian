## 产品与 Schema 强制契约

### 1. Product policy 身份

- `policy_code` 不包含版本号；`policy_version` 独立存储。
- V1 只承认以下组合：
  - `food_expiry` + `1`
  - `pet_expiry` + `1`
  - `general_long_expiry` + `1`
- migration 必须把现有 `food_v1` 明确迁移为 `food_expiry` + `1` + `Managed`；现有食品导入路径只允许做保持当前食品行为所必需的身份归一化。
- 不得改变 `ProductCode`、BatchKey（Product + ProductionDate + ExpiryDate）或其他既有业务身份、唯一索引及生命周期权威。

### 2. ExpiryManagementStatus

新增明确状态：`Managed`、`Excluded`、`Unresolved`。

- `Managed`：`PolicyCode` 必须非空，`PolicyVersion` 必须为正整数。
- `Excluded` / `Unresolved`：`PolicyCode`、`PolicyVersion` 必须同时为空；不得创建占位或伪 policy。
- EF 模型与 SQLite check constraint 必须共同强制上述条件；不能只依赖调用方约定。
- 迁移后的既有 Product 均为 `Managed / food_expiry / 1`。

### 3. scope_key / CategoryCode

- `scope_key` 继续复用 `Product.CategoryCode` 的持久化位置，不新增同义列。
- `CategoryCode` 定义为稳定 canonical 内部编码，不得直接把 Excel 中文显示名称作为永久 identity。
- 本卡保持既有食品 canonical 值 `food`；I02 才负责 10 个源商品大类到 canonical `CategoryCode` 的映射。

### 4. 范围基线

新增最小范围基线实体，唯一身份为：

`ScopeKey + PolicyCode + PolicyVersion`

至少持久化：主键、上述唯一身份、建立 Import、固定业务日期、UTC 建立时间、完成状态/完成时间。`PolicyCode + PolicyVersion` 本身即规则快照身份，不新增重复的规则 JSON、表达式或配置系统。

- `ScopeKey`、`PolicyCode` 非空且去除首尾空白；`PolicyVersion > 0`。
- 一个范围允许先持久化未完成状态，再在同一后续业务事务内完成；本卡只验证持久化契约，不实现冷启动事务。
- 同一唯一身份重复插入必须由数据库唯一约束拒绝；不同 `PolicyVersion` 相互独立。

### 5. BatchBaseline 审计契约

新增批次基线实体，至少包含：

- `BaselineId`
- `BatchId`
- `StageAtBaseline`
- `ColdStartDisposition`
- `CatchupWindowDays`（适用时）
- Task / Catchup 来源（适用时）

`BaselineId + BatchId` 必须唯一。`StageAtBaseline` 复用 canonical Stage：`none / discount_50 / discount_20 / withdraw / expired`。

`ColdStartDisposition` 至少支持：

- `discount50_baseline`
- `discount20_baseline`
- `withdraw_task`
- `expired_today_task`
- `expired_catchup_task`
- `expired_historical_baseline`
- `stock_zero_baseline`

约束：

- `CatchupWindowDays` 仅 `expired_catchup_task` 可有值，且必须为 `3..30`；其他 disposition 必须为空。
- Task / Catchup 来源仅任务 disposition 可有值；`expired_catchup_task` 必须明确记录首次历史补查来源，基线类 disposition 不得伪造 Task 来源。
- 这些记录仅是首次接管审计事实，不得创建或伪造成 `Inspection`、`InspectionItem`、Revision、`LifecycleEvent`、completed Task 或 `HandledAttentionVersion`。
- 本卡只交付实体、映射、约束和持久化测试；不创建真实冷启动批次基线数据。

### 6. 唯一 migration 门禁

- I01 是 V1-F01 计划中唯一允许新增 migration 的任务；必须同时更新 ModelSnapshot。
- migration 必须支持现有 8 条 migration 的旧库升级及空库从零创建；升级不得创建业务 Task/Inspection/基线记录。
- I02--I04 默认禁止新增 migration。若后续发现 schema 不足，必须停止并重新取得产品经理批准，不得绕过或滥用现有字段硬做。

### 7. Reminder 边界

- 本卡不修改 Reminder。
- I04 也不实施“提前 3 天预提醒”；I04 只保证全品类改造不破坏现有 Reminder 消费 open Task 的链路。
- 统一提前 3 天预提醒仍属于后续 V1-F02，当前未获授权。

## Policy 计算最小契约

复用现有 canonical Stage 和优先级，建立最小可测试的 V1 policy 计算入口；不建设规则引擎、插件、配置后台或 UI 计算。

- 月份固定按 30 天：`1/2/3/6/12` 月 = `30/60/90/180/360` 天。
- 到期当天为 `expired`。
- `food_expiry/1`：总效期 `<=270` 天使用 `30/14/7`；`>270` 天使用 `90/60/14`。
- `pet_expiry/1`：使用 `90/60/14`。
- `general_long_expiry/1`：仅总效期 `>180` 天适用 `180/90/14`；`<=180` 天不是 Managed policy 计算结果，保持规则未覆盖语义。
- 不实现食品 7--9 个月低销量人工例外、日用季节性、应季搭配、赠品小样或未知 policy 猜测。
