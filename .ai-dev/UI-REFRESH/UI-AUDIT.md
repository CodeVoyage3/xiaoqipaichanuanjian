# UI/UX 现状审计

> UIUX-R01 / 阶段 8 前置治理文档。审计日期：2026-08-31。本文只记录现状、设计问题和治理边界，不授权生产 UI 实施。

## 1. 审计结论

这是一个原生 WPF 的高频门店业务工具，核心任务是快速识别效期风险、确认批次数量并留下可追溯结果。合适的设计基调是：克制可信、表格优先、状态先于装饰、密度高但不压迫。设计旋钮为：变化度 3、动效 2、密度 8。

当前功能闭环和业务状态已经由 Application/Domain 层建立，主要 UX 债务集中在呈现层：跨页层级不够统一、容器重复偏多、表格密度与窄屏优先级仍需统一、主次操作和危险状态的视觉规则需要治理。结论不是重做业务或重构导航，而是建立一套可在现有 WPF 资源和控件上逐步落地的呈现规范。

## 3. 十类页面审计

### 3.1 Dashboard / 首页

- 现状事实：`MainWindow.xaml:373-592` 已有页面标题、导入数据主按钮、名称/条码/编码搜索、摘要统计、最近导入时间和“优先处理”表格；数据来自 `InspectionTaskQuery.Dashboard`，不是前端计算。
- 主要问题：统计区使用多个带图标的格子，容易被误读成 KPI 墙；摘要、数据新鲜度和优先表的层级还可以更直接；“查看全部待排查任务”是次级导航，不应与主操作竞争。
- 审计方向：首屏先给当前数据是否可用，再给待处理表；统计只保留帮助决策的数字，取消装饰性图标和大字号；优先表的阶段、商品身份、库存、最近有效期、进入详情始终可见。
- 门槛：无导入数据、无任务、加载中、读取错误必须四种可辨状态；不新增虚假导入记录、趋势图或排序逻辑。

### 3.2 待排查任务列表

- 现状事实：`MainWindow.xaml:598-836` 提供搜索、阶段筛选、清空筛选、DataGrid 和分页；`PendingTasksViewModel` 使用固定 50 条分页和 Application 查询。
- 主要问题：搜索和阶段筛选同属一个工具栏但层级不够明确；表格列较多，名称、条码、编码、批次数、库存、日期、操作在 1024 DIP 下需要严格的宽度纪律；筛选为空、真实为空、加载失败的操作路径需保持显著差异。
- 审计方向：搜索为第一焦点，筛选为紧邻的低噪音控制；保留商品名称、商品条码、商品编码、批次数、库存、最近有效期和查看详情；单元格复制反馈使用短时文本提示，不能依赖悬停。
- 门槛：Ctrl+F 聚焦搜索并全选，Tab 顺序可预测，滚轮不会被内嵌表格吞掉；不能在 UI 增加客户端排序或改变分页语义。

### 3.3 排查详情

- 现状事实：`MainWindow.xaml:1570-1998` 展示商品名、条码、编码、库存、待排查批次、正常批次折叠区、草稿状态和底部操作；`InspectionDetailViewModel.cs` 通过草稿、重新确认、库存修正和提交用例调度业务。
- 主要问题：身份信息、库存风险、批次表和底部动作都重要，若继续使用同等圆角容器会削弱阅读顺序；自定义明细表和全局 DataGrid 的行高、边线和焦点表现可能不一致。
- 审计方向：身份和关键库存先于批次表；批次表为主表面，正常批次默认折叠；草稿保存状态固定在底部动作栏旁；“完成排查”是唯一 Primary，清空草稿和修正库存为次级，重新确认只在对应行显现。
- 门槛：空白、0、正数仍是三种输入语义；陈旧批次、超库存、已完成、系统结束、任务不存在和读取错误均须保留现有状态文字与动作约束。

### 3.4 Excel 导入

- 现状事实：`MainWindow.xaml:2006-2232` 为三步导入流程、选文件、预览、异常行表格和确认按钮；`ImportViewModel.cs:9-163,313-476` 管理解析、预览、无变化、确认和失败状态。
- 主要问题：步骤圆点、摘要格和多个 Border 叠加后偏“向导卡片”；文件身份、数据影响和异常行的阅读优先级应高于装饰性的步骤图形。
- 审计方向：步骤只作紧凑进度标记；文件名、身份/陈旧性结论、变更摘要和异常行依次呈现；确认按钮只在有变更且守卫通过时突出；解析和确认使用不确定进度，不显示伪百分比。
- 门槛：Excel 是局部增量而不是全量快照；异常行不阻止其他有效数据导入；取消、失效身份、重复确认、忙碌禁重入和失败重试均保持现有语义。

### 3.5 排查历史

- 现状事实：`MainWindow.xaml:845-1372` 提供历史列表、详情、批次快照和修改历史；`InspectionHistoryQuery.cs:69-218` 负责列表、详情和指定明细修改记录。
- 主要问题：历史列表、详情和修改记录都使用边框表面，信息的时间轴关系不够明显；长商品名、编码和 UTC 时间在窄屏下需要稳定截断、提示和横向访问策略。
- 审计方向：历史列表突出商品身份和正式排查时间；详情明确“快照”性质；修改数量入口只作用于选中明细，结果反馈放在编辑区外并保持可见。
- 门槛：历史表格默认只读；修改必须显式选择、二次确认、非负整数校验；同值不写入新 Revision；不能把历史编辑变成当前任务生命周期操作。

### 3.6 历史明细修改 / Revision 视图

- 现状事实：`MainWindow.xaml:1245-1332` 和 `InspectionHistoryViewModel.cs:190-348` 提供选中明细、修改前后数量、保存/取消和 Revision 表格。
- 主要问题：编辑态与只读快照态的视觉分界需要更强；保存结果若落入折叠区域或短暂提示，长期操作人员难以确认是否写入。
- 审计方向：编辑区使用低饱和警示表面和明确的“只修改数量”说明；保存结果、同值无变化、找不到记录和异常固定在结果区；Revision 表格按时间倒序展示，不用颜色替代数值。
- 门槛：商品身份、其他快照、正式排查时间不可编辑；不能新增生命周期、库存或任务状态按钮。

### 3.7 提醒设置

- 现状事实：`MainWindow.xaml.cs:137-306` 通过原生 WPF 模态窗口编辑每日提醒时间和当前用户自动启动；`ReminderSettingsUseCase.cs:23-60` 只接受 `HH:mm` 并返回保存结果。
- 主要问题：低频设置不应占用主工作区；时间输入、自动启动和保存结果的关系要比装饰性设置卡更清晰。
- 审计方向：保持原生小型模态；标签、格式示例、校验结果、取消和保存顺序固定；自动启动明确标注“当前用户”，不再引入第二套启用状态。
- 门槛：非法时间不提交；保存后按当前用户设置重新调度；取消不改变已提交设置；键盘 Enter/Esc 行为明确。

### 3.8 数据备份与恢复

- 现状事实：`MainWindow.xaml:1373-1505` 展示已验证备份、立即备份和恢复所选备份；`DatabaseBackupRestoreViewModel.cs:258-376` 负责重验证、恢复、重启要求和严重失败锁定。
- 主要问题：危险动作与普通刷新/创建备份在同一工具区，风险层级需要更强；备份文件名、身份、大小、验证状态和恢复后动作要形成一个连续判断路径。
- 审计方向：先说明“仅显示应用验证通过的备份”，再给备份表；立即备份为 Primary，恢复为 Danger 且必须选中目标；恢复确认默认取消，确认文案包含目标文件、当前数据将被替换、恢复后退出/重启。
- 门槛：维护态、忙碌态、恢复成功后必须重启、严重失败锁定和显式退出保持现有状态；UI 不复制 hash、完整性、migration 或 File.Replace 算法。

### 3.9 全局 Shell / 左侧导航

- 现状事实：`MainWindow.xaml:191-313` 提供白色左栏、产品名、版本和六个 NavButton；`Stage4ViewModels.cs:18-34,807-1065` 维护页面枚举、导航和忙碌/保护门禁。
- 主要问题：当前导航顺序和历史基线存在名称/顺序治理需求；导航固定 224 DIP，在 1024x600 与 125% 下压缩内容；选中、禁用和保护锁定状态必须避免只靠颜色。
- 审计方向：保留单一 Shell 和现有页面，不引入二级侧栏；选中项使用位置标记、文本和低饱和填充；低频设置置于底部但不隐藏；版本信息不抢首屏。
- 门槛：导航不能绕过忙碌、草稿稳定保存、维护态或恢复锁定；窗口隐藏到托盘、恢复同一窗口、显式退出和单实例语义不改。

### 3.10 Dialog / Confirmation / Error / Empty state

- 现状事实：`MainWindow.xaml.cs:115-134,241-306,326-398` 使用 OpenFileDialog、原生设置窗口和 MessageBox 处理文件、库存、历史修改、恢复和错误确认；各页面 XAML 已分别包含加载、空、筛选空和错误区。
- 主要问题：状态种类齐全，但视觉语言若继续各页局部实现，容易出现“无数据”“筛选无结果”“读取失败”“危险锁定”相互混淆；危险确认需要明确默认焦点和后果。
- 审计方向：状态组件统一为标题、原因、下一步、可选次级动作四段；空状态不使用大插画；错误提供可执行的重试/返回；危险确认首句说明后果，取消为默认，不用红色覆盖整页。
- 门槛：加载不能伪装为空；筛选空可清除筛选；业务错误不能用成功色；严重失败必须保留锁定和退出路径；对话框名称、Tab 顺序和 AutomationProperties 可被辅助技术读取。

## 4. 共性问题分级

### P0：实施前必须守住的可用性和安全性

1. 业务状态与操作权限必须由现有 ViewModel/Application 用例决定，UI 不复制生命周期、导入删除、库存停止、恢复校验或 migration 规则。
2. 关键身份字段商品名、商品条码、商品编码必须同屏可见并可复制；正式排查数量、库存、有效期和阶段不能只在悬停或颜色中表达。
3. “完成排查”保持详情页唯一 Primary；恢复、清空草稿、历史修改、超库存和库存归零保持显式风险确认。
4. 1024x600 DIP、125% DPI、键盘 Tab/Enter/Esc、焦点环、滚轮边界和 AutomationProperties 是验收门槛，不是后续润色。
5. 加载、空数据、筛选无结果、业务错误、严重失败锁定和重启要求必须各自可判定，不能以统一空白占位代替。

### P1：跨页一致性和高频效率

1. 统一标题、描述、工具栏、主表面和底部动作栏的层级；减少每个区域都包一层圆角 Border 的机械感。
2. 统一 DataGrid 与详情明细表的表头、行高、分隔线、复制反馈和选中/焦点状态；密度优先于装饰留白。
3. 统一阶段标签、成功/警告/危险/重新确认的颜色加文字表达；低饱和语义色不能当作唯一信息。
4. 长文件名、商品名、编码、条码、日期和数字在窄屏下有明确截断、Tooltip 或横向访问策略。
5. 低频设置、危险操作和辅助信息默认弱化，不隐藏高频主操作；不要用图标替代明确中文动作名。

### P2：克制的视觉质量

1. 现有蓝色和浅色表面继续收敛，不增加渐变、玻璃、强阴影、霓虹或营销型插画。
2. 统计摘要只保留决策价值，不做大号 KPI 墙；动画仅用于 0-150ms 的状态过渡和不确定进度反馈。
3. 统一 Microsoft YaHei UI/Segoe UI、4/8/12/16/24/32 间距和小半径控件；优先边框、分隔线和对齐，不以卡片堆叠制造层级。

## 5. 不可越过的业务红线

- Excel 是局部增量，不是全量快照；缺失行不代表删除、归零、停止或恢复。
- Stage 3 Lifecycle、Stage 4 Draft/Reconfirm/InventoryAdjustment/Submission、Stage 5 History/Revision、Stage 6 Reminder/Tray、Stage 7 Backup/Restore 的权威边界不可由 UI 改写。
- UI 只展示 Application 查询/用例返回的事实；不得在 XAML、ViewModel 或视觉资源中推导新的阶段、库存、任务完成或恢复成功语义。
- 正式排查历史/结果 Excel 导出仍为 Deferred；本轮不得顺带实现导出、数据库原始表导出或今日任务快照导出。
- 不改 `App.xaml`、`MainWindow.xaml`、任何 `.cs/.csproj`、依赖、migration、schema 或生产行为作为本审计的交付内容；本文和同目录获批准的治理文档之外，不创建 Stage8 实施任务或 UIUX-R02。
- 现有已验收功能和用户数据不得因视觉重排而改变；任何生产 UI 实施都必须在三类代表页方向得到用户确认后再进入单独任务。

## 6. 审计后的验收门禁

实施前，用户需明确确认：

> 新的整体视觉方向认可，可以按该设计系统进入生产 UI 重构。

确认前只允许继续修订治理文档。确认后也只能按批准的代表页和最小生产变更推进，并分别验证：真实 Release WPF、1024x600、125% DPI、键盘/焦点/复制、表格密度、加载/空/错误/危险状态、数据库和业务回归。审计本身不等于生产 UI 验收。
